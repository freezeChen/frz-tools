# 迭代 6：主功能验证与体验打磨

> 本轮**插在迭代 5 的 5c 之前**（5c–5e 保持停放，见路线图补记十九），定位是**收口而不是
> 加能力**：把主功能欠着的「组合证据」与「上手体验」两笔账还掉，再进安全加固。
> 本文是规格；实现记录与验证记录在文末追加。

## 1. 定位与前置

已具备（带证据）：

- 迭代 0–5b 全部实现并验证：容器 **232/0**、数据库备份合约 **13/0**、legacy 档真机
  **118/0**（蓝绿整轮 **183/0**，含重启验证）、CI run `36367471937` 三个 job 全绿。
- CLI 已有 12 个顶层命令：`--json` 与人类可读双路、退出码映射表（`api/v1/errors.go`）、
  中文帮助与未知子命令报错（`internal/cliutil`）。

缺什么（本轮要还的账）：

- **5b 的组合证据**：批量发布「多台主机上都真的换了版本」**未验证**（迭代 5 文档 §16.3）。
  e2e 证明的是编排与协议接线（同一台机上的多个 `opsd` 实例），「一台机上真的部署成功」
  已由 3b/3c/4b 在容器与真机上证明——缺的是**组合**，补齐需要**两台真实主机**，
  而目前只有一台可用的测试主机（`43.142.95.141`，CentOS 7 / legacy 档）。
- **上手没有入口**：没有 `init`（生成配置骨架）、没有 `status`（一屏看「现在怎么样、
  有没有在跑的操作」）、没有 `version`。新用户的第一步是手工照着 `opsd.example.yaml`
  改配置，而那份示例还缺 `backupStore` 与 `nginx` 两段（结构体里有、示例里没有）。
- **报错可读性**：错误码只体现在退出码，用户看到的文本里没有码，查 `api/v1/errors.go`
  的退出码表得先拿退出码反查；`internal/adapters/config` 的用户可见报错是英文，
  同包 `remote.go` 却是中文（5a 已把校验问题逐条拼进 message，剩下的是**语言不统一**）；
  `operation logs --follow` 留了旗标但报「未实现」。
- **一个 1c 起就记着的部署缺口**：以 root 运行的 opsd 建出的 socket 是 `root:root 0660`，
  **非 root 运维用户用不了 opsctl**（真机实测，1c 文档 §19）。

## 3. 关键决策

### D1：为什么插在 5c 之前

5c 的核心价值（RBAC、审批、操作签名）要等**远程端口真开出去、多人协作**才兑现，而
`remote.listen` **默认是关的**——单机 socket 形态下「能连上就是本地运维」依然成立，
安全加固在这个阶段不阻塞任何事。相比之下，主功能欠着的两笔账更靠近「这个工具敢不敢真用」：
批量发布的组合证据是**正确性**问题，上手与报错体验是**能不能被日常使用**的问题。
为还没启用的场景先加固、让在用的功能带着证据缺口和别扭的体验往前走，顺序是反的。

### D2：`init` = 纯本地的模板生成，不做交互式向导

`opsctl init <路径>` 把**内嵌在代码里**的配置模板写到目标路径，然后提示跑
`opsctl config validate --file <路径>`。不连 daemon、不探测环境、不问任何问题。

- **为什么非交互**：可脚本化、可测试；交互式向导的每一步都得为它造测试装置，而
  配置项的全部解释恰恰是模板注释最擅长的。
- **为什么内嵌**：opsctl 不依赖仓库里的文件（装好的机器上未必有源码树）。
- **单一来源问题**：模板内嵌后与 `opsd.example.yaml` 是两份文本，会漂移。对策不是
  合并文件，而是一条**单元测试断言两者的键集合一致**（解析两份 YAML 比较结构，
  注释不计）——漂移会让测试红，而不是让用户先发现。
- **覆盖保护**：目标已存在时拒绝写入，`--force` 才覆盖。
- **`--remote`**：生成 remote 段**取消注释**的版本（占位地址与证书路径、一个示例
  client 条目），把「开远程」从「照着注释逐行改」变成「填三个值」。生成的文件在填入
  真实证书路径前**启动必然失败**，且失败消息逐条指向缺什么——这是校验该干的活。

### D3：`status` 的一屏范围，以及它为什么需要新端点

`opsctl status` 回答的是「**这台 opsd 现在怎么样**」：daemon/database/workers 的健康、
**最近的操作列表**（有没有在跑的、最近失败的）。没有任何写操作、不做汇总推断。

- **需要新端点 `GET /api/v1/operations`**：今天只有按 id 查（`GET /api/v1/operations/{id}`），
  「有没有在跑的操作」无处可看。列表是**纯新增只读端点**，不碰状态机与数据表。
- `limit` 默认 10、上限 100（超出报 400 `INVALID_REQUEST`），按创建时间倒序；可选
  `status` 查询参数按单个状态过滤（取值即状态机的状态值）。
- 响应为 `{"operations": [...]}`，元素与单条查询**同构**。
- 客户端把 health 与列表拼成一屏：未完成操作（`pending`/`running`）在人类可读输出里
  显式标出；`--json` 输出 `{health, operations}`，字段与 API 逐字段对应。

### D4：错误文本带上错误码

CLI 的错误输出从 `opsctl: <消息>` 变成 `opsctl: <CODE>: <消息>`（码保持英文原样，
消息保持中文）。理由：退出码表按码组织，文本里没有码，用户就得拿「退出码 7」去反查
表——而码就攥在手里却没显示。`--json` 路径不变（结构化字段里本来就有）。
本决策**不新增任何错误码**。

### D5：`operation logs --follow` = 客户端轮询循环，不改协议

`--follow` 基于既有的 `--cursor` 增量拉取，客户端固定间隔（1 秒）轮询，操作到终态后
把剩余日志拉完再退出；Ctrl-C 即停。退出码沿用该操作终态的映射（成功 0、失败走
`api/v1` 退出码表）。理由：服务端推送要么引依赖要么改协议，而轮询在这台工具的
现有形态（客户端本来就靠轮询拿操作状态）里是同一件事的延伸。

### D6：`socket.group` 的语义

```yaml
socket:
  path: /run/opsd/opsd.sock
  mode: 0660
  group: frz-ops        # 新增。省略 = 行为与今天完全一致。
```

- 值为**组名**（`os/user.LookupGroup` 解析）或纯数字 gid；解析失败报 `CONFIG_INVALID`
  启动失败，消息指向这个名字。
- opsd 建 socket 后 chgrp 到该组，`mode` 语义不变。典型用法：root 跑 opsd、
  `mode: 0660` + `group: frz-ops`，运维用户进 `frz-ops` 组即可用 opsctl——
  这正是 1c 真机实测暴露的缺口（`root:root 0660` 把非 root 用户挡在门外）。
- **为什么从 5c 拉前**：它是部署使用体验问题，不是权限模型问题；小、独立、
  不配则行为不变。`SudoConfig`（非 root 运行 opsd 的 sudo 执行路径）**仍留 5c**——
  那是执行模型的决定，不是一行 chgrp。

### D7：6d 的形态——harness 先行，实跑停放，停放条件写死

`test/host` 现在是「一次调用 = 一台主机」：`FRZ_HOST` 单值、opsd 装在目标机本机、
全部操作走本地 socket，**没有任何 `--remote` / `--hosts` 的使用**，也没有证书设施。
本轮补齐支撑能力：

- `FRZ_HOST2` 第二主机寻址（run.sh 与 verify.sh 的阶段编排随之支持两台）；
- **证书供给**：harness 在主机上生成 CA 并给两台机的 opsd 签服务端证书、给控制点签
  客户端证书（e2e 用 `crypto/x509` 现签的同一套做法搬到 shell/openssl）；
- 新增批量断言段：登记两台 target → `app deploy --hosts` → **逐台断言真的换了版本**
  （unit 文件、release 目录、探针上报三个来源互证）→ 准备阶段失败默认一台不动
  （退出码 36、`skipped` 带原因）→ `--allow-partial` → 批次幂等重跑 → 部分失败现场
  处置走查（`note` 记录，不是断言）。

**单台上能验什么**：控制点经**真 TCP + mTLS** 打本机 opsd 的远程端口完成一次
`app deploy --hosts <本机登记名>`。它比 e2e 又进一步（真机、真 systemd、真证书文件、
真网络栈——哪怕是回环），**但不等于跨机**。「两台都真的换版本」的实跑证据在第二台
主机到位之前**停放**，期间维持迭代 5 文档 §16.3 的「未验证」标注不变——这条纪律
写在第 10 节，不因 harness 就绪而松动。

### D8：证据纪律

沿用仓库既有约定：断言数以脚本运行时打印的「`%d` 项通过，`%d` 项失败」为准，不引用
静态推导值；「Linux 容器」与「Linux 主机」是两类证据不得混用；任何一条在证据拿到
之前只能写「未验证」。

## 4. 配置增量

```yaml
socket:
  path: /run/opsd/opsd.sock
  mode: 0660
  group: frz-ops     # 6c 新增，可选。省略 = 与今天逐字节一致。
```

- 校验：`group` 给了就必须能解析（组名或纯数字 gid），失败报 `CONFIG_INVALID`；
  不给则不校验、不 chgrp。
- `opsd.example.yaml` 补上 `backupStore` 与 `nginx` 两段（注释形态，与 init 模板同键集），
  并加入 `socket.group` 的注释条目。
- 除此之外**不改任何配置段**；`remote` 段的校验语义不变。

## 5. API 增量

| 端点 | scope | 说明 |
| --- | --- | --- |
| `GET /api/v1/operations` | read | 最近操作列表：`limit`（默认 10，上限 100，非法报 400 `INVALID_REQUEST`）、可选 `status` 过滤（单个状态值）；按创建时间倒序；响应 `{"operations": [...]}`，元素与 `GET /api/v1/operations/{id}` 同构 |

## 6. CLI 增量

| 命令/行为 | 说明 |
| --- | --- |
| `opsctl init <路径> [--force] [--remote]` | 生成 opsd 配置骨架（D2）。本地动作，不连 daemon |
| `opsctl status` | health + 最近操作一屏（D3）；`--json` 输出 `{health, operations}` |
| `opsctl version` | 客户端构建版本；**默认不连 daemon、退出码恒 0**，`--daemon` 才连并追加对端版本（连不上显式标注，不报错）——把「可能慢/可能失败」的路径变成显式选择 |
| `operation logs --follow` | 落地（D5）：基于 `--cursor` 的轮询循环 |
| 错误输出格式 | `opsctl: <CODE>: <消息>`（D4），文本与 `--json` 两路都带码 |

帮助文本占位符统一为 `<name>` 风格（现状 `<主机...>` 与 `<name>` 混用）。

## 7. 数据表：**不动**

6a–6d 都不改表、不加表。操作列表端点读的是既有 `operations` 表；
`socket.group` 是运行时文件系统动作，不落库。

## 8. 兼容性与迁移影响

- **默认行为逐字节不变**：`socket.group` 不配则行为与今天一致；`init`/`status`/`version`
  是纯新增命令；`GET /api/v1/operations` 是纯新增只读端点。
- **错误文本格式变化**：`opsctl: <CODE>: <消息>` 会改变 stderr 的形状——凡是断言
  旧文本的测试同步更新；脚本如果解析 stderr（不该解析，退出码才是接口）会受影响，
  在提交信息与文档里写明。
- **config 报错中文化**：消息语言变化，`Details["problems"]` 与逐条拼接的结构不变，
  API 调用方不受影响；断言英文消息的测试同步更新。
- **`operation logs --follow`**：从「显式报未实现」变为可用——旧行为的报错测试删除。
- **`make verify-linux` 的断言数**：6c 会加（socket 属组/ACL），以脚本运行时打印的
  数字为准；6a/6b 不引入内核级语义，容器断言数预期不变。

## 9. 验收标准

每一条都给「命令 / 结果 / 证据类型」。

### 9.1 6a：CLI 上手三件套

1. **init 生成即合法**：`opsctl init /tmp/opsd.yaml` 生成文件，
   `opsctl config validate --file /tmp/opsd.yaml` 通过；目标已存在且无 `--force` 时
   拒绝且不改动原文件。【集成测试】
2. **模板与示例同键集**：解析 init 模板与 `opsd.example.yaml`，两者的键集合一致
   （含 `backupStore`/`nginx` 的注释段）。【单元测试】
3. **`--remote` 版本在填真值前起不来**：对 `--remote` 生成的文件直接启动 opsd，
   失败且消息逐条指向缺的证书文件。【集成测试 / Linux 容器】
4. **status 一屏**：起一个 opsd、提交一个长操作后 `opsctl status`：健康四项 +
   最近操作列表，未完成操作显式标出；`--json` 的 `{health, operations}` 字段与 API
   对应。【集成测试 / e2e】
5. **列表端点参数**：`GET /api/v1/operations` 默认 10 条；`limit=101` → 400
   `INVALID_REQUEST`；`status=running` 只回 running。【集成测试】
6. **远程只读身份可用**：`read` 档位的远程身份调用 `status` 与列表端点成功，
   打写端点仍 `REMOTE_FORBIDDEN`。【e2e】
7. **version**：`opsctl version` 打印客户端构建版本且退出码 0（daemon 不存在也不失败）；
   `--daemon` 时追加对端版本。【集成测试】
8. **回归**：`make ci` 全绿，既有断言一条不少。【静态 / 单元 / 集成 / e2e】

### 9.2 6b：输出与报错打磨

1. **错误文本带码**：制造 `LOCK_BUSY`（同一 resource 提交两个操作）→ stderr 出现
   `LOCK_BUSY:`，退出码不变。【集成测试】
2. **config 报错中文化**：构造三处不合法的配置，`config validate` 与 opsd 启动的
   消息逐条列出、语言为中文、字段路径保持英文原样。【集成测试 / Linux 容器】
3. **follow 落地**：提交一个有日志输出的长操作，`operation logs --follow` 持续输出
   直到终态后退出；成功退出码 0、失败走退出码表。【集成测试】
4. **占位符统一**：`opsctl <命令> --help` 的用法行占位符风格统一。【静态检查】
5. **回归**：`make ci` 全绿。【静态 / 单元 / 集成 / e2e】

### 9.3 6c：socket 属组

1. **不配则不变**：不配 `socket.group` 的 opsd，socket 的属主与模式与今天一致，
   既有容器断言原样通过。【Linux 容器】
2. **配了即生效**：`socket.group` 指向一个组 → socket 属组为该组、模式不变；
   **该组成员的**非 root 用户能连上 socket 并成功执行只读命令。【Linux 容器】
3. **组名不存在拒绝启动**：`group: no-such-group` → 启动失败，`CONFIG_INVALID`
   消息指向该名字。【集成测试】
4. **真机**：root 跑的 opsd 配 `group` + 非 root 运维用户 `opsctl health` 成功
   （补上 1c §19 那条实测缺口）。【Linux 主机】
5. **回归**：`make verify-linux` 全绿，断言数以实跑打印为准。【Linux 容器】

### 9.4 6d：批量组合证据（harness 先行）

1. **单台可验部分**：真机上，控制点经真 TCP + mTLS 打本机 opsd，完成一次
   `app deploy --hosts <本机登记名>`：批次报告逐台给出结论，部署真的换了版本
   （unit 文件 / release 目录 / 探针上报三处互证）。【Linux 主机】
2. **证书供给**：harness 生成的 CA 与证书让 `host check` 对两台（或单台阶段的一台）
   都报 `backend: tls` 且身份正确。【Linux 主机】
3. **两台都真的换版本**（**停放待第二台主机**，到位后执行）：两台机的上述三处
   互证全部通过。【Linux 主机】
4. **准备阶段失败默认一台不动**（**停放待第二台主机**）：停掉一台的 opsd →
   退出码 36、另一台零操作、报告 `skipped` 带原因。【Linux 主机】
5. **幂等重跑与 `--allow-partial`、部分失败现场处置走查**（**停放待第二台主机**）。
   【Linux 主机】

## 10. 已冻结的决定（用户 2026-09-30 拍板）

1. **本轮插在 5c 之前**，定位「验证主功能 + 体验打磨」；5c–5e 停放不变。
2. **第二台真机暂时没有**：6d 本轮做到 harness 与证书供给 + 单台可验部分；
   「两台都真的换版本」等实跑证据**停放待主机到位**，期间**不得写成已验证**。
3. **5c 只拉 `socket.group`**；`SudoConfig`（sudo 执行路径）与 sudoers/PAM 实际
   策略验证留在 5c。
4. **API 只加 `GET /api/v1/operations` 一个只读端点**；不新增错误码、不改状态机
   与数据表。

## 11. 未验证内容（规格阶段就写明）

- **批量发布「多台主机上都真的换了版本」**：停放待第二台真实主机（6d 验收标准
  9.4 第 3–5 条）。harness 就绪**不等于**证据到手。
- **legacy 档 systemd 232–239**：无对应版本的主机，本轮不解决。
- **strict 档真机复跑**（`192.168.11.101` 整段网段从本机不可达）：本轮不解决。
- **`socket.group` 与 SELinux enforcing 的交互**：真机验证时顺带观测并记 note，
  但不作为验收标准（本工具不提供 SELinux 加固，这一条保持「未实现」的措辞）。
- **大规模（几十上百台）并发压测**：本轮不碰。
- **`SudoConfig` / sudoers/PAM 实际策略、RBAC、审批、操作签名、审计导出**：5c。
- **metrics、通知、发布报表**：5d。**备份灾备**：5e。
