## 4. 运行模型

```text
opsctl
  │ Unix Socket / HTTP JSON
  ▼
opsd HTTP API
  │
  ├─ OperationService：幂等、状态、取消、重试、审计
  ├─ LockManager：资源锁
  ├─ Executor：argv 进程执行
  └─ SQLiteStore：操作、日志、锁、审计、migration
```

`opsctl` 不直接修改目标系统。需要执行操作时由 `opsd` 创建并持久化 Operation，再由后台 worker 执行。查询接口优先从 SQLite 读取，保证 CLI 与 daemon 重启后仍可查询历史。

## 5. 对外协议草案

### 5.1 通用约定

- API 前缀：`/api/v1`。
- 内容类型：`application/json`。
- 长操作创建返回 HTTP `202 Accepted` 和 `operationId`。
- 所有响应包含 `apiVersion`，错误响应包含稳定 `code`、人类可读 `message` 和可选 `details`。
- 客户端可发送 `Idempotency-Key`；服务端不把密钥写入普通日志。
- 默认 CLI 输出人类可读文本，`--json` 输出原始 JSON。

### 5.2 端点

#### `GET /api/v1/health`

返回 daemon、数据库和 worker 状态。健康检查本身不创建 Operation。

#### `POST /api/v1/operations`

请求最小结构：

```json
{
  "kind": "executor.command",
  "resource": "demo-resource",
  "dryRun": false,
  "spec": {
    "argv": ["/usr/bin/true"],
    "workingDirectory": "/var/lib/opsd/work",
    "environment": {}
  }
}
```

要求：

- `argv` 非空，程序路径必须经过配置的执行策略校验。
- 不接受一整段 shell command 字符串。
- `dryRun=true` 时只校验和记录计划，不启动进程。
- `resource` 用于并发锁；相同资源默认禁止并发执行。

#### `GET /api/v1/operations/{id}`

返回 Operation 当前状态、阶段、时间、退出码、错误码、重试关系和 dry-run 标记。

#### `POST /api/v1/operations/{id}/cancel`

向运行中的 Operation 发出取消请求。服务端通过 context 取消进程，记录取消事件和最终结果。

#### `POST /api/v1/operations/{id}/retry`

只允许对失败、取消或 daemon 重启中断的 Operation 重试。重试创建新的 Operation ID，并通过 `retryOf` 保留关联关系；不复用原幂等键。

#### `GET /api/v1/operations/{id}/logs`

按时间顺序返回结构化日志，支持 `cursor`、`limit` 和 `follow=false`。本迭代可先实现查询，流式 follow 保留接口兼容性。

## 6. 领域模型与状态机

### 6.1 Operation

核心字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 不透明 Operation ID |
| `kind` | 操作类型，例如 `executor.command` |
| `resource` | 被锁定的资源标识 |
| `status` | `pending`、`running`、`succeeded`、`failed`、`cancelled`、`rolled_back` |
| `phase` | 当前阶段，例如 `validate`、`execute`、`finalize` |
| `dryRun` | 是否只生成计划 |
| `idempotencyKey` | 幂等键，服务端唯一作用域内唯一 |
| `requestHash` | 请求规范化后的摘要，用于检测同键不同请求 |
| `retryOf` | 关联的原 Operation ID |
| `exitCode` | 外部进程退出码，可为空 |
| `errorCode` | 稳定错误码，可为空 |
| `createdAt/startedAt/finishedAt` | 生命周期时间 |
| `createdBy` | 调用方标识，可为空 |

状态约束：

```text
pending ──> running ──> succeeded
                    ├──> failed
                    └──> cancelled

failed/cancelled ──> retry ──> pending（新 Operation）
```

`rolled_back` 为后续发布流程保留的终态，本迭代不主动产生该状态。

### 6.2 幂等

- `Idempotency-Key + 请求作用域` 建立唯一约束。
- 同一 key 且 `requestHash` 相同：返回原 Operation。
- 同一 key 但 `requestHash` 不同：返回 `IDEMPOTENCY_CONFLICT`。
- 幂等判断与 Operation 创建必须在同一数据库事务中完成。

### 6.3 资源锁

- 锁以 `resource` 为唯一键，记录 owner Operation ID、获取时间和释放时间。
- 锁获取与状态从 `pending` 到 `running` 在同一事务中完成。
- 已被其他未完成 Operation 占用时返回 `LOCK_BUSY`，不等待、不执行。
- daemon 启动恢复时释放属于遗留 `running` Operation 的锁。
- 释放操作必须校验 owner，避免旧 worker 释放新 Operation 的锁。

### 6.4 重启恢复

daemon 启动时在事务中：

1. 查找所有 `running` Operation。
2. 将其标记为 `failed`，错误码设为 `DAEMON_RESTARTED`。
3. 写入系统审计事件和恢复日志。
4. 释放对应资源锁。
5. 保留原 Operation 的输入和输出，等待显式 retry。

不自动续跑可能有副作用的外部命令。恢复的是状态、审计和锁的一致性，而不是未经确认地重放命令。

## 7. 持久化设计

SQLite 要求：

- 开启 WAL。
- 开启 foreign keys。
- 设置合理 busy timeout。
- migration 版本单调递增并在启动时执行。
- 数据库路径、文件权限和备份策略由配置控制。

首个 migration 至少建立：

### `operations`

存储 Operation 主记录、状态、幂等字段、时间、退出码和错误信息。

### `operation_logs`

存储 Operation ID、级别、时间、阶段、消息和脱敏后的结构化字段；支持按 Operation ID 和时间查询。

### `resource_locks`

存储资源唯一键、owner Operation ID、获取时间和释放时间。

### `audit_events`

存储事件类型、主体、Operation ID、资源、结果、时间和不可变事件详情。

### `schema_migrations`

记录已应用 migration 版本和应用时间。

## 8. Executor 约束

Executor 接口至少提供：

```go
type Executor interface {
    Run(ctx context.Context, spec CommandSpec) (Result, error)
}
```

其中 `CommandSpec` 包含：

- `Argv []string`
- `WorkingDirectory string`
- `Environment map[string]string`
- `Timeout time.Duration`
- `MaxOutputBytes int64`
- `SensitiveEnvKeys []string`
- `DryRun bool`

行为要求：

- 使用 `exec.CommandContext` 或等价非 shell 调用。
- 超时返回 `EXEC_TIMEOUT`，取消返回 `EXEC_CANCELLED`。
- 非零退出返回 `EXEC_EXIT_NONZERO`，并保留退出码。
- stdout/stderr 超过上限时截断并记录 `outputTruncated=true`。
- 日志中隐藏敏感环境变量、凭据值和命令参数中声明为敏感的字段。
- dry-run 不创建目标文件、不启动子进程。

### 对协议和错误码的补充（兼容性影响）

1. 新增错误码 `INVALID_REQUEST`，HTTP 400，CLI 退出码 2。用于请求体非法、`spec` 不合法、
   `argv` 为空或非绝对路径、对不可重试状态调用 retry 等输入错误。该错误码不与既有错误码冲突，
   只是在原先只能返回 `INTERNAL` 的场景提供更准确的分类。
2. 明确 `LOCK_BUSY` 的语义：`resource` 上存在任何**未完成**（`pending` 或 `running`）Operation 时，
   新的提交直接返回 `LOCK_BUSY`（HTTP 409，CLI 退出码 4），不排队、不等待。这与第 6.3 节
   “已被其他未完成 Operation 占用时返回 LOCK_BUSY，不等待、不执行”一致，代价是不做请求排队。
   由此形成不变量：同一 `resource` 任意时刻最多存在一个未完成 Operation。worker 在
   `pending` → `running` 时仍会在同一事务中重新校验并获取锁，作为并发提交的第二道防线。
3. 状态机保持第 6.1 节的严格形式，未新增 `pending → failed`。校验失败、超时、取消都发生在
   已经进入 `running` 之后。

### 锁、幂等和恢复的实现要点

- 锁的获取与 `pending` → `running` 在同一事务内完成；释放时校验 `owner_operation_id`，
  避免旧 worker 释放新 Operation 的锁。
- SQLite 使用 WAL、`foreign_keys`、`busy_timeout=5000` 和 `_txlock=immediate`，并在连接池中
  限制为单连接写，避免 `SQLITE_BUSY`。
- 守护进程启动时把遗留 `running` Operation 标记为 `failed` / `DAEMON_RESTARTED`、写审计与日志、
  释放锁，且不重放任何命令。
- 长任务执行期间不持有数据库连接：worker 在短事务中领取后提交，再启动进程。
- 执行器只接受 argv，不使用 shell；通过 `exec.CommandContext` 实现超时与取消；输出超限截断并
  标记 `outputTruncated`；日志中的敏感 argv 位置和敏感环境变量值被替换为 `[redacted]`。

自动化测试覆盖的验收标准：

- `opsctl health` 连接本地 `opsd`（`test/e2e`，真实二进制 + 真实 Unix Socket）。
- 相同幂等键只执行一次（`test/e2e` 用追加写入文件计数断言行数为 1）。
- 并发提交同一 `resource` 时只有一个获得锁，其余退出码 4。
- dry-run 不创建文件、不启动进程。
- 执行器不经过 shell（argv 中的 `$(whoami)` 不被展开）。
- 超时、取消、非零退出、输出截断、敏感信息脱敏均有单元测试。
- 守护进程重启后状态、审计、锁一致，`DAEMON_RESTARTED` 可查询。

### 补充验证：Linux 容器 2026-09-21

- 执行者：Command Code agent

- 证据类型：**Linux 容器**（新增证据类型，见下）

**证据类型新增强制约定**：「Linux 容器」与「Linux 主机」是两类不同证据，不得混用。
容器验证的是内核级语义（文件模式、Unix Socket ACL、用户/属组、`runuser` 的行为），
**不能**替代真实主机验证：真实 reboot 后 unit 的持久化、SELinux/AppArmor 约束、
sudoers/PAM 的实际策略、真实主机安装规范。

本节的手工探测已固化为自动化 harness：`test/linux/`（`Dockerfile.systemd` + `verify.sh`），
用 `make verify-linux` 运行，共 22 项断言，覆盖上表全部内容，并作为独立 job 接入 CI。
（该 job 在 2026-09-22 推送远程仓库后才首次真实执行，当时断言已增至 40 项并全绿；
见路线图「2026-09-22 远程仓库落地，CI 首次真实执行」。）
错误退出已通过反向验证确认：把 socket 模式故意改成 `0666` 后，会产生 2 项 FAIL 并以非零退出，
证明该 harness 不是空转。

另有一条实践约束：**不得把 macOS 目录 bind mount 进容器做权限测试**。virtiofs 不保真
文件属主与模式，结果不可信；二进制应通过容器内构建或 `docker cp` 进入，测试状态留在
容器文件系统内。

### 仍未验证的内容（不得用源码检查替代）

以下内容在本次验证后**仍未验证**：

未验证，因为它本身尚未实现。

`.github/workflows/ci.yml` 已在 Ubuntu 上执行格式检查、vet、单元/集成/e2e 测试与交叉编译，
但 CI 通过同样**不**代表上述 Linux 专属行为已经验证。
