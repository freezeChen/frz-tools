## 1. 定位与前置

迭代 2 让 opsd 能**按计划备份数据库与目录资源**，并且能**验证备份真的可用**。
它把迭代 1 的底座组装成一个完整的运维闭环：`Schedule`（1b）决定何时做，任务引擎
（迭代 0 + 1d）负责执行、重试与审计，`StorageBackend`（1a）负责内容寻址的落盘，
`SecretRef`（1a）负责凭据。

**入口条件已达成**：路线图定义迭代 2 的入口是「1a + 1c 完成」，两者均已实现并提交。
1d 的重试也已实现，本迭代的「失败可重试」直接复用了它（只增补了两个错误码，
见第 13 节的偏离 6）。

**复用的边界**：本迭代不新建存储层、不新建调度器、不新建执行器。所有外部命令仍走
`Executor` 端口（argv-only、**永不经过 shell**），凭据仍只经 `SecretRef` 解析。

## 2. 范围与里程碑拆分

迭代 2 的内容量级接近迭代 1（迭代 1 被拆成 1a/1b/1c/1d 四个里程碑），因此**建议同样拆分**。
拆分的判据是「哪一层可以独立验证」：

| 里程碑 | 内容 | 为什么能独立验证 |
| --- | --- | --- |
| **2a** | `BackupPolicy` 模型、`BackupAdapter` 端口与共享合约测试、**文件/目录备份适配器**、元数据持久化、`backup run\|list\|verify` 的 API+CLI | 文件备份不需要数据库实例，容器里就能端到端跑完「备份→校验→恢复→比对」 |
| **2b** | PostgreSQL 与 MySQL/MariaDB 适配器，`restore --mode isolated`（临时实例/临时目录） | 需要真实数据库实例（集成测试与容器） |
| ~~**2c**~~ | ~~传输编码：gzip 压缩、AES-256-GCM 加密、摘要与原子提交~~ **已并入 2a**（2026-09-24 决定 A） | 见第 13 节偏离 1：摘要不可能不在 2a，且加密默认开启时不做加密的 2a 在默认配置下跑不起来 |
| **2d** | ~~GFS 保留策略~~（2026-09-24 移出，见第 22 节）、`prune`、隔离 restore 的完整验证链 | 依赖 2a/2b/2c 的产物 |

**本规格的职责**是冻结**跨切面决策**（端口形状、策略模型、编码与摘要的归属、元数据与
保留模型、存储根的隔离），这些必须**一次定死**，否则每个切片会各定一套。实现按里程碑
逐片交付；**建议先冻结并实现 2a**，它给出第一个可端到端验证的闭环。

### 2a 实现

- `BackupAdapter` 端口与共享合约测试（`internal/application/backupcontract`）。
- `BackupPolicy` 领域模型：版本化信封、严格解码、校验与默认值。
- 文件/目录备份适配器（`internal/adapters/backup/files`）：路径、排除规则、符号链接策略。
- 备份元数据持久化（migration `0006`）与 `backup_policies` / `backups` 两张表。
- `backup.run` / `backup.verify` 走 Operation（异步、可查询、可取消、可重试）。
- `backup list|show` 与 `app` 系列的 CLI/API 风格一致。
- 独立备份存储根（`backupStore.root`）。
- **调度器支持 `backup.run`**（见 D6：`Schedule` 目前写死了 `executor.command`）。

### 迭代 2 整体不实现

- **数据库主从切换、在线 schema migration、跨数据库事务备份**（路线图第 11 节已明确不做）。
- **密钥管理**（生成、轮换、托管）：密钥由运维放进既有凭据目录，opsd 只读取（D4）。
- 增量/差异备份：2a–2d 只做**全量**备份。「增量」需要每个适配器定义自己的变更基准，

- 备份内容的**异地/远程复制**（迭代 5 的远程与多主机范畴）。
- Nginx 蓝绿与发布（迭代 4）。
- metrics 与通知接口（迭代 5）。

## 3. 关键决策

### D1：适配器产出**逻辑备份流**；摘要、加密与原子提交由应用层统一负责

```go
type BackupAdapter interface {
	// Validate 只校验策略能否被本适配器执行，不产生任何副作用。
	Validate(ctx context.Context, policy *domain.BackupPolicy) error

	// Preflight 检查连接、客户端版本、磁盘空间、目标存储可达性与凭据可解析。
	// 必须在 Backup 之前完成，且不得留下任何备份产物。
	Preflight(ctx context.Context, policy *domain.BackupPolicy) (domain.PreflightReport, error)

	// Backup 把逻辑备份流写进 w，并返回本次备份的自述元数据。
	// 实现方不得自行压缩、加密或计算摘要——那些属于应用层（见下）。
	Backup(ctx context.Context, policy *domain.BackupPolicy, w io.Writer) (domain.BackupMetadata, error)

	// Restore 从 r 读回逻辑备份流并恢复。mode 决定恢复到目标还是隔离环境。
	Restore(ctx context.Context, policy *domain.BackupPolicy, r io.Reader, mode domain.RestoreMode) error

	// Verify 校验备份流的自洽性（如 tar -t、pg_restore --list），**不接触目标资源**。
	Verify(ctx context.Context, policy *domain.BackupPolicy, r io.Reader) error

	// Cleanup 释放本适配器在本次操作中产生的临时资源（临时目录、临时恢复实例）。
	Cleanup(ctx context.Context, policy *domain.BackupPolicy, operationID string) error
}
```

**为什么摘要、加密、原子提交必须在应用层**：它们是**安全与一致性边界**，下放给每个适配器
等于让「每种数据库各实现一套加密」，任何一处写错都是静默的数据泄露或静默的不可恢复。
`StorageBackend` 只需要 digest、不接受调用方文件名（1a 的结构性保证）也要求由应用层
统一计算摘要。

**压缩的归属**：由 `encoding.compression` 声明（`none` / `gzip`），**应用层执行**；
例外是使用数据库原生归档格式时压缩已由工具完成（`format: custom`），应用层**不再叠加**。

### D2：`Cleanup` 是**释放适配器侧临时资源**，不是保留策略

路线图第 5 节把「清理」列在 `BackupAdapter` 下，容易被读成「删除旧备份」。**必须澄清**：
「哪些备份该删」由 GFS 保留策略决定，那是**通用逻辑**，属于应用层（D3）；适配器的 `Cleanup`
只负责释放它自己在本次操作中造的临时目录 / 临时恢复实例。

理由是结构性的：保留策略一旦抽象进适配器，每个适配器都要实现一遍 GFS，
而它们对「一次备份」的理解各不相同，最后必然漂移成三套语义。

### D3：保留策略是通用的，属于应用层；GFS 不抽象进适配器

沿用 1a 制品 GC 的既有形态（`ArtifactService.Collect(ctx, keepLast, olderThan, dryRun)`），
在其上扩展 GFS 维度。**`prune` 是同步用例而不是 Operation**——它只改元数据与删 blob，
与制品 GC 一致；长耗时的删除能力留给将来（若真出现，再引入异步 prune）。

### D4：加密的密钥只来自 `SecretRef`，opsd **不做密钥管理**

`encoding.encryption.keySecret` 是一个 `SecretRef`（`kind: env` / `kind: file`），密钥由
运维放进既有的凭据目录（`/etc/opsd/secrets`，`0600`，1c 已实现并验证的读取路径）。
算法 AES-256-GCM 分块，**密钥标识（key id）写进备份元数据**，便于将来轮换时知道哪个备份
用的是哪把钥匙。

**不做**：生成密钥、轮换密钥、托管密钥、密钥托管服务。这些是运维职责，opsd 只读不写。
密钥解析失败时**不得**降级为「不加密」——必须让备份失败（静默降级成明文备份是最坏的结果）。

### D5：备份写到**独立的存储根**，与制品分开

**这是一条防数据丢失的结构性要求。** 1a 的制品 GC 在回收时会顺手清理「孤儿内容」，
而它的判据是**「这个 digest 不在 `artifacts` 表里」**：

```go
// internal/application/artifact.go（现状，Collect 的孤儿回收段）
entries, err := s.store.List(ctx)
for _, entry := range entries {
    if live[entry.Digest] {   // live 只由 artifacts 表的行填出来
        continue
    }
    s.store.Delete(ctx, entry.Digest)   // ← 不在制品表里 = 删
}
```

因此，只要备份 blob 与制品共用一个根，`artifact gc` 会把**每一个备份**都当成孤儿删掉
——不是个别残片，是全部备份内容。这是**静默的数据丢失**，且只有在真正要恢复时才会发现。

因此：配置新增 `backupStore.root`（与 `artifactStore.root` 并列），**备份只写自己的根**，
两条 GC 各自只扫自己的根。相应地，备份自己的孤儿回收（崩溃在落盘与写库之间留下的 blob）
也必须**只看备份根**，不得顺带清理制品根。

### D6：调度器需要能触发 `backup.run`——`Schedule` 目前写死了 `executor.command`

1b 的调度循环在创建 Operation 时**硬编码**了 kind：

```go
// internal/application/scheduler.go（现状）
hash, err := requestHash(v1.KindExecutorCommand, schedule.Resource, false, schedule.Spec)
```

因此今天一个 `Schedule` **只能**触发 `executor.command`。迭代 2 要按计划跑备份，必须让
计划能声明「触发哪种操作」。做法：`Schedule` 新增**可选**字段 `operationKind`，
省略时默认 `executor.command`（向后兼容，既有计划行为逐字节不变，**不提升 apiVersion**），
调度器改为按该字段分派，而不是写死常量。

**同时**：`backup.run` 的操作与 `runtime.*` 一样，执行时读**当前**策略而不是创建时的快照
（与 1c 的既有语义一致）。计划里的 `operationKind` 只决定「建哪种操作」，
策略内容以执行时刻为准。

### D7：恢复必须**显式确认**，且默认只允许恢复到隔离环境

路线图要求「恢复默认需要显式确认和独立权限」。据此：

- `backup.restore` 分两档：`isolated`（恢复到临时目录/临时实例，完成后销毁，用于验证）
  与 `inPlace`（恢复到策略声明的真实目标）。
- `inPlace` 必须显式带上确认标志，否则返回 `BACKUP_RESTORE_UNCONFIRMED`。
  显式确认不是形式主义——恢复会**覆盖真实数据**，这是本工具里破坏性最强的动作。
- `inPlace` 的恢复对象必须与备份的 `resource` 一致（不允许跨库/跨目录恢复），
  防止「拿 A 库的备份恢复到 B 库」这类误操作。

### D8：同一资源默认禁止并发备份，且与 1a/1c 一致地用 `resource` 锁表达

备份与恢复都占 `resource` 锁（既有机制），因此同一资源的两个备份天然互斥，
不需要新机制。**恢复与备份也必须互斥**（同一个资源的锁），否则会出现「备份到一半、
恢复把数据改了」的产物不确定。

### D9：未完成或校验失败的对象**不得**进入清理范围

沿用路线图的表述并落到实现：`backups` 表里只有 `status = succeeded` **且**校验通过
（或在配置的宽限期内尚未校验）的行才参与保留策略计算；`pending` / `running` / `failed`
的行**不参与**，也不计入 `keepLast`。删除 blob 之前必须先标记元数据（先标记、后删内容），
这样中断时最坏留下一个无主的 blob（可由孤儿回收处理），而不会留下「元数据说在、内容没了」。

## 4. 模型冻结（`BackupPolicy` manifest）

沿用 `ApplicationSpec` 的做法（`apiVersion` 信封 → 迁移链 → `KnownFields(true)` 严格解码）：

```yaml
apiVersion: ops.frz.io/v1alpha1
kind: BackupPolicy

name: orders-nightly            # 资源名，同时是 Operation 的 resource

resource:
  kind: files                   # files | postgres | mysql
  # kind=files
  paths:
    - /var/lib/orders/data
  exclude:
    - "*.tmp"
    - "cache/**"
  symlinks: skip                # skip | follow | error（默认 skip）
  # kind=postgres|mysql（2b 起）
  dsnSecret: orders-db-url      # SecretRef 名，绝不内联明文
  database: orders

encoding:
  compression: gzip             # none | gzip（默认 gzip）
  encryption:
    enabled: true               # 默认 true
    keySecret: backup-key       # SecretRef；enabled=true 时必填

retention:
  keepLast: 14
  keepDays: 30
  gfs:
    daily: 7
    weekly: 4
    monthly: 6

timeout:
  backup: 1h
  restore: 2h
```

校验要求（全部返回 `MANIFEST_INVALID`）：

- `name` 沿用 application 的字符集（它是安全边界：会进入存储前缀与日志）。
- `resource.kind` 必须是已注册的适配器种类；`files` 的 `paths` 非空且**必须都是绝对路径**，
  且**不得包含 `..`**（路径穿越）。
- `exclude` 只允许相对模式；`symlinks` 只允许三个取值，且**默认 `skip`**——
  `follow` 会让备份跟随链接逃出 `paths` 范围，属于显式承担风险的选择。
- `encoding.encryption.enabled = true` 时 `keySecret` 必填；`keySecret` 只允许写成
  Secret 引用名，**不允许内联明文**（内联明文会被写进数据库与审计）。
- `retention` 至少给出一项，否则备份会无限增长；各项非负。
- `timeout` 必须为正。

## 5. 持久化（migration `0006_backups.sql`）

```sql
CREATE TABLE backup_policies (
    id          TEXT PRIMARY KEY,
    name        TEXT NOT NULL UNIQUE,
    policy_json TEXT NOT NULL,
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL,
    updated_by  TEXT
);

CREATE TABLE backups (
    id                TEXT PRIMARY KEY,
    policy_id         TEXT NOT NULL REFERENCES backup_policies (id),
    operation_id      TEXT REFERENCES operations (id),
    status            TEXT NOT NULL CHECK (status IN ('pending','running','succeeded','failed','pruned')),
    storage_digest    TEXT,            -- 内容寻址的 digest；successeded 必有
    logical_bytes     INTEGER,         -- 逻辑流字节数（压缩前）
    stored_bytes      INTEGER,         -- 落盘字节数（压缩加密后）
    compression       TEXT,
    encryption_key_id TEXT,            -- 便于将来轮换时知道用哪把钥匙
    resource_kind     TEXT NOT NULL,
    server_version    TEXT,
    client_version    TEXT,
    tool              TEXT,
    labels_json       TEXT,            -- GFS 标签等
    started_at        TEXT NOT NULL,
    finished_at       TEXT,
    verified_at       TEXT,
    verified_ok       INTEGER,
    error_code        TEXT,
    error_message     TEXT
);

-- 保留策略按「策略 + 完成时间」倒序取，索引覆盖这一段。
CREATE INDEX ix_backups_policy_finished ON backups (policy_id, finished_at DESC);
-- 「这个 digest 有没有备份元数据」是孤儿回收与删除前的检查。
CREATE INDEX ix_backups_digest ON backups (storage_digest) WHERE storage_digest IS NOT NULL;
```

**兼容性**：全是新建表，**不动任何既有表**，升级与回滚都不影响迭代 0/1 的数据。

## 6. API 与 CLI

| 端点 | 说明 |
| --- | --- |
| `PUT /api/v1/backup-policies/{name}` | 提交/覆盖策略（严格解码 + 校验） |
| `GET /api/v1/backup-policies/{name}` | 读取策略 |
| `GET /api/v1/backup-policies` | 列出策略 |
| `POST /api/v1/backups` | 触发一次备份，返回 Operation（异步） |
| `GET /api/v1/backups` | 列出备份（按策略与时间过滤，游标分页） |
| `GET /api/v1/backups/{id}` | 单个备份的元数据 |
| `POST /api/v1/backups/{id}/verify` | 校验一个已存在的备份（异步 Operation） |
| `POST /api/v1/backups/{id}/restore` | 恢复（异步 Operation，`inPlace` 需显式确认） |
| `POST /api/v1/backups/prune` | 按保留策略清理（**同步**，支持 `dryRun`，与制品 GC 一致） |

```bash
opsctl backup policy put --file orders-nightly.yaml
opsctl backup policy list
opsctl backup run --policy orders-nightly --json          # 返回 operation id
opsctl backup list --policy orders-nightly
opsctl backup verify <backup-id>
opsctl backup restore <backup-id> --mode isolated         # 默认档
opsctl backup restore <backup-id> --mode inPlace --confirm
opsctl backup prune --policy orders-nightly --dry-run
```

错误码与退出码增量（沿用既有风格，退出码接在 22 之后）：

| 错误码 | HTTP | 退出码 | 用途 |
| --- | --- | --- | --- |
| `BACKUP_NOT_FOUND` | 404 | 2 | 备份或策略不存在 |
| `BACKUP_PREFLIGHT_FAILED` | 409 | 23 | 预检未通过（连接、版本、空间、凭据） |
| `BACKUP_VERIFY_FAILED` | 409 | 24 | 校验不一致 |
| `BACKUP_RESTORE_UNCONFIRMED` | 409 | 25 | `inPlace` 恢复未显式确认 |
| `BACKUP_IN_USE` | 409 | 26 | 该备份正在被操作，或删除被拒绝 |
| `BACKUP_KEY_UNRESOLVED` | 400 | 27 | 加密密钥无法解析（**不得降级为明文**） |

策略本身的非法沿用既有的 `MANIFEST_INVALID`（400/17）与 `MANIFEST_CONFLICT`（409/18）——
`BackupPolicy` 与 `ApplicationSpec` 一样是版本化 manifest，不另立一套错误码。

## 7. 兼容性与迁移影响

- 全是新增：新表、新端点、新 kind、新配置段（`backupStore.root`）。
- **唯一触及既有代码的地方**是 D6：`Schedule` 新增可选 `operationKind`，
  调度器由「写死 `executor.command`」改为按字段分派。省略该字段时行为与现在**逐字节一致**，
  属于同一 `apiVersion` 内的向后兼容变更，**不提升 apiVersion**。
- `backupStore.root` 未配置时，备份相关端点返回 `CONFIG_INVALID`（与 `artifactStore.root`
  未配置时禁用制品端点的既有做法一致），**不影响** opsd 启动。

  `retention` 全空被拒、负重值被拒。
- GFS 保留策略：给定一批完成时间，断言「保留集合」符合 daily/weekly/monthly 语义
  （这是最容易被实现成「差不多」的一块，必须表驱动）。
- 路径安全：`files` 适配器的路径解析、排除规则、符号链接三种策略的行为。
- 未完成/失败的行不计入 `keepLast`（D9）。

### 共享合约测试（`internal/application/backupcontract`）

任何 `BackupAdapter` 实现都必须通过，语义与 `runtimecontract` 同源：

- `Validate` 对合法策略通过、**无副作用**；对非法策略拒绝。
- `Preflight` 不得产生备份产物。
- `Backup` → `Verify` → `Restore`（隔离模式）→ **内容比对一致**（往返正确）。
- 中断语义：`Backup` 中途被取消时，`Cleanup` 之后不留适配器侧临时资源。
- 同一策略重复 `Cleanup` 幂等。
- **`files` 适配器是本合约的第一个真实实现**；`postgres`/`mysql`（2b）必须过同一套。

### 集成

## 9. 验收标准（2a）

1. `BackupPolicy` 非法在提交时即失败（`MANIFEST_INVALID`），且无任何副作用。
2. `files` 适配器通过 `backupcontract` 的**全部**断言，含「备份 → 校验 → 隔离恢复 → 内容一致」往返。
3. 备份内容**内容寻址**：同一份数据重复备份产生相同 digest；digest 与内容不符时备份失败。
4. 备份写入**独立的存储根**；制品 GC 运行后备份内容**完好无损**（D5）。
5. `backup.verify` 走 Operation（可查询、可取消）；校验不一致时报 `BACKUP_VERIFY_FAILED`。
6. `backup restore --mode inPlace` 未加确认时被拒绝（`BACKUP_RESTORE_UNCONFIRMED`）。
7. 同一 `resource` 的备份与恢复**互斥**（复用 `resource` 锁，不需要新机制）。
8. 中断安全：备份进程被杀死或 opsd 重启后**不产生**「成功」记录，
   且该次产生的残片不进入保留策略范围。
9. 保留策略只作用于 `succeeded` 且已校验的行；`prune --dry-run` 不产生任何删除。
10. 加密关闭时备份可读；加密开启且密钥无法解析时**备份失败**（`BACKUP_KEY_UNRESOLVED`），
    **绝不**静默产出明文备份。
11. 调度：带 `operationKind: backup.run` 的计划能触发备份；省略时既有行为不变。
12. `make ci` 与 `make verify-linux` 全绿，迭代 0/1a/1b/1c 的回归用例全部继续通过。

### 决定 1：采纳 2a–2d 的拆分 —— **采纳**

按第 2 节的四片交付，**先冻结并实现 2a**（端口、策略模型、共享合约测试、文件备份适配器、

*理由*：跨切面决策一次定死、实现逐片交付——这正是迭代 1 拆成 1a–1d 的做法。

### 决定 2：备份与制品**不共享配额** —— 配置上分列、各自独立计数

`artifactStore.quotaBytes` 与 `backupStore.quotaBytes` 分别计数。

*理由*：物理上是同一块盘，但备份天然比制品大得多，混在一个配额里会出现「传个制品」
因为「备份占满了」而失败，且难以排查。独立计数、由运维按盘的总容量自行分配。

### 决定 3：加密**默认开启**，`keySecret` 必填 —— 按推荐

`encryption.enabled: true` 为默认（与路线图「备份文件默认加密」一致），且该开关打开时
`keySecret` 必填。因此**未配置密钥的部署必须显式把加密关掉**才能用。

*理由*：这个摩擦是刻意的——它迫使「不加密」成为一个被写下来的决定，而不是默认发生的事。

### 决定 4：GFS 标签按时区感知的日/ISO 周/自然月判定 —— 按推荐

备份**完成时刻**落在哪一天 / 哪一周 / 哪一月就带哪个标签；周的边界按 ISO 8601
（周一为第一天），月的边界按自然月，**时区取计划声明的时区**（与 1b 的调度时区一致）。
跨时区部署必须显式声明，**不依赖主机本地时区**。

### 决定 5：`prune` **同步** —— 按推荐

与制品 GC（`POST /api/v1/artifacts/gc`，已核实为同步端点）保持一致；备份数量或删除量超过
阈值时打一条 warn 日志。若实测发现同步 prune 会阻塞 HTTP 处理（例如上千个备份），
再引入异步——届时按新规格走，不在这里预留。

### 决定 6：恢复的「独立权限」**记为未实现** —— 当前架构下不做

路线图要求「恢复需要显式确认和独立权限」。冻结为：

- `inPlace` 恢复的**显式确认**是本阶段唯一的门槛；
- **「独立权限」明确记为未实现**，留给迭代 5 的生产加固。

*理由*：opsd 目前只有 Unix socket 的文件模式一层访问控制，**能连上 socket 的人就能恢复**。
在没有认证体系的情况下假装有「独立权限」是自欺，比记为未实现更危险——它会让运维以为
存在一道实际不存在的防线。

## 12. 与 1d 的推进顺序

1d（重试与并发策略）的规格已冻结但尚未实现。路线图第 5 节把「网络中断、空间不足、

### 逐文件要点

**领域（`internal/domain/backuppolicy.go`、`backup.go`）**
- `BackupPolicy`：资源（files 的 paths/exclude/symlinks，或 postgres/mysql 的 dsnSecret/database）、
  传输编码、GFS 保留、超时。校验里几处是**安全边界**而不是格式偏好：paths 必须绝对、不含 `..`、
  不能是 `/`；symlinks 默认 `skip`（follow 会顺着链接跑出声明范围）
- **加密默认开启**：wire 上用 `*bool`。`bool` 的零值是「关闭」，会把「没写」静默解释成
  「不加密」——那正好是最危险的方向。代价是未配密钥的部署必须显式写 `enabled: false`
- 密钥只以 `SecretRef`（kind + name）出现：结构上就没有内联明文的表达方式
- `Backup` 与 `Operation` 的状态刻意分开：Operation 说「这次动作跑得怎么样」，
  Backup 说「这份备份能不能用」。`Usable()` 要求 succeeded **且**已校验通过

**manifest 解析（`internal/adapters/manifest/decode.go`、`backuppolicy.go`）**
- 把「信封 → 迁移链 → KnownFields 严格解码」抽成 `decodeManifest`，由 ApplicationSpec 与
  BackupPolicy **共用**：各写一份必然漂移，而漂移的表现恰好是「用户以为字段生效了、
  其实被静默丢掉」。两种 manifest 的迁移链分开登记

**持久化（`migrations/0006_backups.sql`、`internal/adapters/sqlite/backup.go`）**
- `backup_policies` 与 `backups` 两张表，全是新建。`SaveBackupPolicy` 以 name 为键 upsert，
  **冲突时保留原有 id**（指向它的历史备份不该改归属）
- `FailStaleBackups` 把重启遗留的 running 备份收成失败（由 `Recover` 调用）

**传输编码（`internal/backupcodec/codec.go`）**
- 先压缩再加密（反过来无意义）。流自描述（头部带 flag），读侧不需要外部告诉它加没加密
- AES-256-GCM 分块（64 KiB），每块独立随机 nonce，**分块序号进附加认证数据**：
  重排或删除中间分块会被拒绝
- 已加密的流以**零长度明文的分块收尾**：没有它，在分块边界上被截断的流看起来就是一次正常
  的 EOF，而「悄悄少了一段数据」是备份最坏的一种失败
- 密钥用 sha256 派生；密钥**标识**是摘要前 8 字节（回答「用哪把钥匙」，不足以还原密钥）

**编排（`internal/application/backup.go`）**
- 适配器产出逻辑流 → 编码 → `StorageBackend.Put`，用 `io.Pipe` 串成流水线：
  不要先攒到内存，整份读进内存正是备份工具在真实数据上会破的地方
- 逻辑字节数在**明文一侧**统计（压缩比要靠它和落盘字节数一起才算得出来）
- 备份记录**先**以 running 落库，只有真正写完才 succeeded
- 密钥解析失败**绝不**降级为不加密
- 恢复模式随 Operation 存下（`RestoreOptions`），原地恢复的确认在**创建期**检查

**装配与配置**
- `backupStore.root` 与 `artifactStore.root` **分开**，配额各自独立计数（决定 2）
- 备份类操作与 runtime.* 走同一条 `Service.Create`，没有第二条旁路

### 对规格的补充与偏离

1. **2c 并入 2a（用户决定 A，2026-09-24）**。规格原本把传输编码放在 2c，但 2a 的验收标准与
   这个拆分自相矛盾：标准 #3 要求「内容寻址」，而摘要不可能不在 2a（`StorageBackend.Put`
   本来就必须收 digest、`backups.storage_digest` 也是 schema 的一部分）；标准 #10 关于
   加密失败的要求，在加密未实现时无意义；且**加密默认开启**，不做加密的 2a 交付的东西
   在默认配置下根本跑不起来。因此 **2c 里程碑取消**，压缩、加密、密钥解析与密钥标识一次做完。

2. **`keySecret` / `dsnSecret` 用 `SecretRef`（kind + name）而不是规格 §4 YAML 里的裸名字**。
   理由：与决定 4「凭据只经 SecretRef」一致，而且结构上就没有内联明文的位置——
   「密钥不会被写进数据库」不是靠字符串校验拦住的，是没有表达方式。

3. **`timeout` 用秒数（`backupSeconds`/`restoreSeconds`）而不是规格 §4 的 `backup: 1h`**。
   仓库里时长在 wire 上已有既定惯例（`intervalSeconds`、`startTimeoutSeconds`、
   `baseDelaySeconds`），同一概念引入第二种写法是将来要还的债。

4. **不加 `max_attempts` 列**（规格第 6 节列了 `attempt`/`max_attempts`/`not_before`/
   `retry_policy_json` 四列）。理由与 1d 相同：**列放可变状态**（`attempt`），
   **JSON 放不可变策略**（`retry_policy_json` 里的 `maxAttempts`）。两者并存是第二份会漂移的真相来源。

5. **备份类操作拒绝 `dryRun`**（规格未提及）。适配器端口没有 dry-run 语义：接受它就会变成
   「以为只是预演、其实真的备份了或恢复了」，而恢复是破坏性动作。预演请用 `backup verify`
   或 `--mode isolated`。

6. **备份失败纳入 1d 的重试白名单**（对 1d 一条**已冻结决定**的修订）。路线图要求备份
   「标记失败并可重试」，而 1d 的白名单里只有 `EXEC_*`/`RUNTIME_NOT_READY`/`DAEMON_RESTARTED`，
   备份的瞬时失败以 `BACKUP_*` 呈现、不在其中。增补 `BACKUP_PREFLIGHT_FAILED` 与
   `BACKUP_VERIFY_FAILED`；**刻意不加** `BACKUP_KEY_UNRESOLVED` 与 `BACKUP_RESTORE_UNCONFIRMED`。
   已在 1d 文档第 3 节 D3 的表格里就地注明（加行 + 说明），不删原文、不放宽判据。

7. **容器镜像加装 `sqlite3`**（`test/linux/Dockerfile.systemd`）。`check_backup` 要直接查库
   看落盘产物，端口上没有对应的读取方法。镜像需要 `--rebuild` 才会带上它。

### 发现

1. **加密会破坏内容寻址去重——这是有意为之的取舍，但验收标准 #3 必须精确化。**
   加密流每块用独立随机 nonce（GCM 的正确用法，不能改成确定性的），因此同一份内容加密两次
   得到不同字节、不同 digest。于是：加密**关闭**时「同内容同 digest」字面成立、可以去重；
   加密**开启**时（**这是默认**）不做去重。所有带客户端加密的备份系统都是这个取舍。
   **实现没有偏离规格，是规格的 #3 表述需要精确化**；已在本节与判定表里写明。

2. **`audit_events.operation_id` 有指向 `operations(id)` 的外键**，而 `FinishBackup` 一开始
   把**备份 ID** 填进了那个字段 → `FOREIGN KEY constraint failed`。改为填发起这次备份的
   Operation，备份 ID 进 `details`，两个方向都可查。**由集成测试抓出**。

3. **未配备份存储根时，读取类端点照常工作、只有执行类拒绝**。这不是规格里的规定，是实现
   时定下的取舍：看一眼有哪些策略、哪些备份不需要存储根，把这些也拒掉只会让排查更难。
   端点用例按这个实际行为断言，并把取舍写进了注释。

4. **`prepareDirectories` 曾把未配置的 `backupStore.root`（空串）交给 `MkdirAll`**，于是
   「备份功能没启用」变成「opsd 起不来」。空路径要跳过。**由 e2e 抓出**。

## 17. 2b 设计决定（2026-09-24，实现前冻结）

2b 的范围是 PostgreSQL 与 MySQL/MariaDB 适配器，以及数据库的隔离恢复（规格第 2 节）。
`BackupAdapter` 端口形状与 `BackupPolicy` 模型在 2a 已冻结，2b **不改它们**。
但落地时发现三件事在 2a 的规格里没有答案，必须先在实现之前定下来。

### D10：数据库适配器需要**流式执行**——`Executor` 端口新增 `RunStream`

**现状是一个正确性缺陷，不是性能问题。** `Executor.Run` 把命令的 stdout 收进一个
**有上限**的缓冲（`maxOutputBytes`，默认 1 MiB）：

```go
// internal/adapters/executor/executor.go（现状）
stdout := newLimitedBuffer(maxOutput)   // 超过上限的部分被丢弃，只置 Truncated 标志
cmd.Stdout = stdout
```

用它跑 `pg_dump`，超过上限的部分会被**丢掉**，而 `pg_dump` 照常退出 0——于是备份记录是
`succeeded`，内容却是残缺的。**「备份成功但内容是残缺的」是备份工具最坏的一类失败**：
它不会在备份时暴露，只会在真要恢复时暴露。

因此 `Executor` 端口新增：

```go
// RunStream 以与 Run 完全相同的语义执行命令（argv-only、allowedPaths 校验、超时、
// 取消、同一套错误码），差别只在 stdout 与 stdin 是**流**而不是内存缓冲。
RunStream(ctx context.Context, spec domain.CommandSpec, in io.Reader, out io.Writer) (domain.Result, error)
```

**兼容性影响**：这是内部端口的新增方法，非对外 API——`api/v1` 的类型、错误码与
`apiVersion` 均不变，不涉及数据表。所有实现者（本机执行器与测试假实现）需要补上。

两处必须处理的细节（实现记录里会给出对应断言）：

- **stdout 写入失败必须杀掉子进程**。`os/exec` 在 `Stdout` 不是 `*os.File` 时会起一个
  拷贝协程，而 `Wait` 先等进程退出、再串行地收拷贝协程的错误。若我们的写入方先失败
  （例如存储层报错、管道被关），拷贝协程停下、子进程却阻塞在写满的管道上——
  **双方互等**。做法是让写入失败**取消运行上下文**，`CommandContext` 的看门狗随即杀掉子进程。
- **stdin 读取失败不得被当成「命令正常收尾」**。读取失败时管道关闭，子进程看到的是
  EOF：`psql` 完全可能因为 SQL 已经读完而**退出 0**，于是半份数据被当成一次成功的恢复。
  因此读取错误必须优先于退出码上报。

### D11：压缩归属按工具行为定，且在**提交期**校验

规格 D1 说「使用数据库原生归档格式时压缩已由工具完成，应用层不再叠加」，但没说
**谁来保证这两件事一致**。定为：

| 资源 | 工具与格式 | 策略必须声明 | 理由 |
| --- | --- | --- | --- |
| `postgres` | `pg_dump --format=custom`（归档自带压缩） | `encoding.compression: none` | 再压一遍只是白烧 CPU 与时间；写 `gzip` 在提交期被拒（`MANIFEST_INVALID`） |
| `mysql` | `mysqldump`（纯 SQL 文本） | 默认 `gzip`，也可以写 `none` | 文本可压且压得动，应用层压是净收益 |

**MariaDB 的工具名与 MySQL 不同，名字要按优先级找**（实现时在真实实例上撞到的）：
MariaDB 从 10.5 起把 `mysqldump` / `mysql` 改名为 `mariadb-dump` / `mariadb`，而且
**有些客户端包不再提供旧名字**——官方 `mariadb:11` 镜像里就只有 `mariadb-dump`。
只认 MySQL 的名字，会让「支持 MariaDB」这句话在真实的 MariaDB 主机上落空，而且表现成
「工具没装」，把排查带偏。因此 `mysql` 适配器按 `mysqldump → mariadb-dump`、
`mysql → mariadb` 的优先级解析，并把**实际用到**的那个名字写进备份元数据的 `tool` 列。

让策略显式声明、由适配器在 `Validate` 里核对，比让应用层「猜这个工具压没压」可靠：
猜错的方向是「压了两遍」（浪费）或「以为压过其实没有」（备份体积失控），而显式声明
错误的方向是**提交时被拒绝**。

### D12：数据库的隔离恢复 = **同一实例上的临时数据库**，不是临时实例

规格与路线图写的是「临时实例/临时目录」。「临时实例」意味着起一个完整的 PostgreSQL/MySQL
进程：需要数据目录、端口、初始化、root 权限，成本与风险都远超收益，且在 opsd 这个
「不做进程编排之外的事」的架构里没有位置。因此定为：

- `isolated`：在**同一实例**上建一个临时数据库（名字带随机后缀），恢复到它，完成后删除。
  它证明「这份归档真的能恢复」，且**不碰真实数据库**。
- `inPlace`：恢复到策略声明的真实数据库，需显式确认（规格 D7）；
  恢复前用 `--clean --if-exists` 清掉归档里会重建的对象。

**代价必须写清楚**（不写就等于假装它是完整的隔离）：

1. 需要**建库权限**与对端磁盘空间；没有权限时隔离恢复失败，这是预期行为。
   **2026-09-24 在真实主机上补全（见第 21 节）**：PostgreSQL 侧是 `CREATEDB`（建库的人
   自动成为属主，因此够了）；**MySQL 侧不止于此**——建库的人**不会**自动获得该库的权限，
   所以在临时库里恢复还需要临时库上的权限。实测的最小权限配方是
   `GRANT CREATE ON *.*` + `GRANT ALL PRIVILEGES ON \`frz\_restore\_%\`.*`；
   只给前者会让每一次隔离恢复都在对端留下一个临时库。
2. **覆盖不到实例级对象**（角色、表空间、全局设置）——临时库在同一个实例里，
   恢复进去的只是库内对象；
3. 崩溃可能留下孤儿临时库：临时库名由适配器在内存里跟踪、由 `Cleanup` 删除，
   与 `files` 适配器的临时目录是同一套办法、同一个残余风险。**记为已知限制**，
   运维可用 `frz_restore_%` 前缀排查。

### D13：DSN 只接受 URI 形式，且 `resource.database` 必须与 DSN 里的库名**一致**

- 接受：`postgres://` / `postgresql://` 与 `mysql://` 的 URI。
- 拒绝：libpq 的 `keyword=value` 连接串。理由：它有自己的转义规则（引号、反斜杠），
  自己实现一份的结果是**连接串被静默改变**——连错库比连不上坏得多。拒绝时给出可执行的提示。
- **`resource.database` 必须与 DSN 里的库名相等**，否则预检失败。这条挡的是
  「策略里写 `orders`、DSN 却指着生产库」这类误配置：备份跑得好好的、备的却是另一个库。
- **`resource.database` 的字符集另有约束**（实现时补上的，规格原文没有）：只允许
  字母、数字、下划线与 `$`，且不以数字开头。这是**安全边界**而不是格式偏好——库名会进
  命令行（mysql 的位置参数）与连接串（postgres 的 URI 路径），一个以 `-` 开头的库名会被
  MySQL 客户端当成**旗标**解析。执行器只接受 argv、永不经过 shell，因此它挡得住 shell
  注入，但挡不住旗标注入，这一条补上那个缺口。
- **密码只经环境变量传递**（`PGPASSWORD` / `MYSQL_PWD`），不进 argv。argv 会出现在
  `ps` 的输出里；环境变量只对同用户与 root 可见。DSN 里的其余部分（主机、端口、用户、
  库名、`sslmode` 等）不含密码，进 argv 无害。
- 明文 DSN 只在**使用时刻**由 `SecretResolver` 解析，不落库、不落日志（与 1a 的凭据约定一致）。

### D14：`backup verify` 补上**摘要校验**（修 2a 的一个漏洞）

路线图的验收标准写的是「备份文件可通过 checksum 验证」，但 2a 的 `ExecuteVerify` 只做了
「解码 + 让适配器自检」，**没有核对 `backups.storage_digest`**：存储层按 digest 定位文件，
却从不重算内容摘要，因此「文件被改坏/换掉」在含压缩或加密时也许还能被发现
（gzip 有 CRC、加密流有终结块），在 `compression: none` + 不加密时**完全发现不了**。

改法：把存储的原始读端包一层 `domain.Hasher`，一边解码一边算，读完后与
`backup.StorageDigest` 比对，不一致返回 `BACKUP_VERIFY_FAILED`。单次读、O(1) 内存。

### D15：数据库适配器 `Verify` 的判据，以及它的**强度边界**（附实测）

| 资源 | 判据 | 说明 |
| --- | --- | --- |
| `postgres` | `pg_restore --list`（目录可读）+ `pg_restore --file=/dev/null`（把每个数据块解出来丢弃） | 不需要数据库连接 |
| `mysql` | 读完整流，在**尾部窗口**里找 `mysqldump` 自己写的结束行 `-- Dump completed on ...` | 截断必然丢标记，因此能发现任意位置的截断 |

**实测数据**（PostgreSQL 16.15，94 KB 自定义归档；`test/linux` 之外的临时容器里跑的
一次性探针，用于选型，不作为交付证据）：

| 手段 | 截断到 99% | 90% | 50% | 砍掉末尾 500 字节 |
| --- | --- | --- | --- | --- |
| `pg_restore --list` | 通过 | 通过 | **通过** | 通过 |
| `pg_restore --file=/dev/null` | 通过 | 拒绝 | 拒绝 | 通过 |

因此结论必须写清楚：**适配器自带的 `Verify` 不是完整性校验**——`--list` 只读目录不读数据，
`--file=/dev/null` 读遍数据块但末尾几百字节的缺失它也不报错。整份流的完整性由
**D14 的摘要校验**与**传输编码**（gzip 的 CRC、加密流的零长度终结块）负责；
适配器 `Verify` 回答的是另一个问题：**「这个工具能不能读懂这份归档」**。

**MySQL 的结束标记是工具自己写的，必须实测确认而不是照文档写**：实测（MySQL 8.0.46
与 MariaDB 11.8.9、客户端与服务端同为容器里的真实实例）默认都会写
`-- Dump completed on ...`，而 `--skip-comments` 会**去掉**它——因此 `mysqldump` 的参数里
**不得**出现 `--skip-comments`，否则校验判据会静默失效。

**开头的自我标识两家不一样**（真实实例上撞到的第二处）：MySQL 8.0 写 `-- MySQL dump ...`，
**MariaDB 11.8 写 `-- MariaDB dump ...`**。只认前者，会让每一份 MariaDB 的备份都校验不通过
——而「校验把好备份判成坏的」比漏检更让人不敢用这个功能。两行都认。

**还有一处只有真实工具才能撞出来**：`--connect-timeout` 是 `mysql` **客户端独有**的选项，
`mysqldump` 不认它——给了就是 `unknown variable 'connect-timeout=15'` 并直接退出 7。
因此连接参数分成两份：两个工具都认的最小公共子集（host / port / user）给 dump 用，
客户端独有的选项只给 `mysql` 用。这条单测（假实现）永远发现不了。

### D16：错误码增量

| 错误码 | HTTP | 退出码 | 用途 |
| --- | --- | --- | --- |
| `BACKUP_RESTORE_FAILED` | 409 | 28 | 恢复失败（工具非零退出、隔离库建不出来、流解不开……） |

规格第 6 节的错误码表**没有**这一项，而 2a 的恢复失败只能借 `EXEC_EXIT_NONZERO` 之类的码
来表达，那会把「备份恢复失败」和「一条命令跑失败」混成同一个东西。**刻意不加入 1d 的
重试白名单**：恢复会覆盖真实数据，自动重试该由人看着做（失败后由运维显式
`operation retry`）。数据库适配器其余失败沿用既有码：预检不通过用
`BACKUP_PREFLIGHT_FAILED`、密钥解析不了用 `BACKUP_KEY_UNRESOLVED`（绝不降级为明文）。

### D17：数据库适配器的**候选实现范围**

`postgres` 与 `mysql` 两个适配器都必须过 `backupcontract` 的**全部**断言
（规格第 8 节）。合约里「隔离恢复不改动资源」与「备份后清空再原地恢复，内容一致」
对数据库适配器的含义是：隔离恢复落到临时库、原地恢复落到 `policy.resource.database`。
适配器的 `Preflight` 额外做两件别处做不了的事：

1. **客户端版本必须不低于服务端主版本**——`pg_dump` 版本低于服务端会直接拒绝工作，
   早点说清楚比让 `Backup` 中途失败好；
2. **库名一致性**（D13）。

### 逐文件要点

**端口与执行器（`internal/application/ports.go`、`internal/adapters/executor`）**
- `Executor` 新增 `RunStream(ctx, spec, in, out)`。理由见 D10：`Run` 会把 stdout 收进
  **有上限**的缓冲，超限部分被丢掉而命令照常退出 0——拿它跑 `pg_dump`，得到的是一份
  **记录为成功、内容却残缺**的备份。这不是性能问题，是正确性问题。
- `Run` 与 `RunStream` 收敛到同一个 `execInternal`：校验、超时、取消与错误分类只有一份。
  两处只有真实进程才撞得出来的细节各自带注释与用例：stdout 写入失败必须取消上下文去杀
  子进程（否则 `os/exec` 的拷贝协程与子进程互等，命令永不结束）；stdin 读取失败必须优先于
  退出码上报（`cat` / `psql` 读不到更多数据时会**正常退出 0**，半份数据会被当成恢复成功）。

**共用部分（`internal/adapters/backup/dbtools`）**
- 凭据解析、工具定位（解析成**绝对路径**——执行器的 `allowedPaths` 按绝对路径比较；
  分工是适配器决定用哪个工具、配置决定它允许待在哪儿）、隔离恢复的临时库名与跟踪清理、
  把工具的执行失败整理成带码错误（`ToolFailure`：`force` 为空则保留执行器的码，
  非空则换成备份域的码；取消/超时/权限一律原样上抛，因为那三个码各自对应上层一套决策）。
- 临时库名：`frz_restore_<清洗过的策略名>_<8 位十六进制>`。清洗是必需的——未加引号的
  标识符在 PostgreSQL 里会被折叠与截断，而**超长标识符是被静默截断的**，于是
  `DROP DATABASE` 拿着一个更长的名字去删，删不掉还不报错。名字总长受 63 字节（两家的
  公共上限）约束，随机后缀必须留住，它是唯一性所在。

**PostgreSQL（`internal/adapters/backup/postgres`）**
- `pg_dump --format=custom --no-owner --no-acl --dbname=<不含密码的 URI>`；密码经
  `PGPASSWORD` 进环境变量。选自定义格式的理由是它能被**离线**校验。
- DSN 只接受 URI；`--dbname` 用的是剥掉密码、其余参数原样的连接串，所以 `sslmode` 之类的
  选项不会在「我们自己重新拼一遍」时丢掉。
- 校验：先 `peekMagic` 看 `PGDMP`（空流 / 截断在开头 / 拿错文件这三件事的原因完全不同，
  而 `pg_restore` 对它们说的是同一句），再 `pg_restore --file=/dev/null --exit-on-error`
  把目录与每个数据块解出来丢弃——不接触目标资源、不需要凭据。
- 隔离恢复：`CREATE DATABASE`（临时库）→ `pg_restore` 到临时库 → `DROP DATABASE`。
  **先登记再创建**：登记在创建之后的话，「建完了、还没登记」这一瞬间崩溃就留下一个
  谁也不知道的孤儿库。`psql` 一律带 `--set=ON_ERROR_STOP=1`——没有它，SQL 失败时
  `psql` 也退出 0，「查不到版本」会伪装成「版本是空串」。

**MySQL / MariaDB（`internal/adapters/backup/mysql`）**
- `mysqldump --single-transaction --routines --events --triggers --no-tablespaces <库>`；
  密码经 `MYSQL_PWD` 进环境变量。
- **刻意不用 `--databases`**：那个选项会在流里写入 `CREATE DATABASE` 与 `USE <原库>`，
  而隔离恢复是把流喂给临时库的——里面的 `USE` 会**切回真实库**，于是「隔离」恢复直接写到
  生产上。不用它，恢复目标就完全由我们传给客户端的库名决定。单测里有一条断言钉死这件事。
- **刻意不用 `--skip-comments`**：它会把结束行一起去掉，而校验判据正是那一行。
- 校验不调任何外部工具、连凭据都不用：读完整流，在头尾各留一个 8 KiB 的窗口，检查开头的
  自我标识与结尾的结束行。**任何位置的截断都必然丢掉结束行**，因此这条判据比 postgres 那边
  还强（见 D15 的实测）。
- 恢复用 `mysql <库>` 读 stdin：非交互模式下它遇错即退，半份数据不会被当成恢复成功。

**应用层（`internal/application/backup.go`）**
- `SavePolicy` 除了领域模型校验，再走一遍**适配器**的校验。「这个 kind 本版本有没有
  适配器」「这份声明与工具的实际行为一致吗」都是适配器才知道的事，让它们在第一次备份
  跑到一半才失败，等于把一份必然失败的策略存进库。执行期的同一道判断保留：库里可能留着
  旧版本写下的策略，或者有人绕过服务直接写库。
- **摘要校验（D14）**：校验时除了问适配器「你读得动吗」，还核对存储字节与
  `backups.storage_digest`。摘要算在**解码之前**的字节上，单次读、O(1) 内存。恢复刻意
  不做这个核对：流是边读边往目标写的，等读完才知道摘要对不对时，数据已经写进去了。
- **`Cleanup` 终于有人调**：每次操作结束（无论成败）都收尾一次，用**不带取消**的上下文
  加固定超时——操作被取消时 `ctx` 已经死了，而收尾恰恰是取消之后最该做完的事。

### 对规格的补充与偏离（2b）

第 17 节已逐条记录（D10–D17）。这里只列**规格原文没有、实现时补上的**四条：

1. **`resource.database` 的字符集约束**（D13 的补充）：挡住 argv 旗标注入。
2. **`SavePolicy` 收紧为「没有适配器的 kind 不许存」**：2a 时允许存下来再在执行期失败，
   理由是那时 postgres/mysql 确实还没实现；两者都有了适配器之后，存一份必然跑不起来的
   策略只剩坏处。
3. **MariaDB 的工具名回退**：见 D11 的补充。
4. **`backup verify` 补上摘要校验**（D14）：这是 2a 的漏洞，不是 2b 的新功能——路线图的
   验收标准写的是「备份文件可通过 checksum 验证」，而 2a 的 verify 只问了适配器。

### 发现（2b）

前三条是**真实数据库实例跑出来的**，单测（假实现）不可能发现：

1. **`mysqldump` 不认 `--connect-timeout`**（它是 `mysql` 客户端独有的选项）→
   `unknown variable 'connect-timeout=15'`，退出 7。连接参数因此分成「两个工具都认的公共
   子集」与「客户端独有」两份。
2. **MariaDB 的客户端包里可能没有 `mysqldump` / `mysql` 这两个名字**：官方 `mariadb:11`
   镜像里只有 `mariadb-dump` / `mariadb`。适配器按优先级解析两个名字，并把**实际用到**的
   那个写进 `tool` 列。否则「支持 MariaDB」在真实 MariaDB 主机上会落空，还表现成「工具没装」。
3. **MariaDB 的备份流开头是 `-- MariaDB dump`**，不是 `-- MySQL dump`。只认后者会让每一份
   MariaDB 的备份都校验不通过——「校验把好备份判成坏的」比漏检更让人不敢用这个功能。
4. **端口的 `Cleanup` 在产品路径上从来没人调**（2a 遗留，读代码时发现）。它有实现、有合约
   测试，但没有任何产品代码调用它，于是「被中断的恢复留下的临时资源」在生产上没有任何出口。
   已补上（每次操作结束都收尾）并有一个记录型适配器的用例钉住它。
5. **2a 的 `backup verify` 不核对 digest**（对照路线图验收标准时发现）：存储层按 digest
   **定位**文件却从不**重算**摘要，因此一份 `compression: none` 且不加密的备份被改坏或换掉
   时，校验会一路通过。已补上（D14）。
6. **`pg_restore --list` 不是完整性校验**（实测，用于选型）：见 D15 的表。它只读目录，
   把一份 94 KB 的归档截断到一半它照样返回 0。

### 发现 1（产品侧：隔离恢复对账号权限的实质要求）

**容器 harness 用的是 root，因此这条要求从来没被暴露过。** 真机上按最小权限给账号，隔离
恢复连着失败两轮，每一轮都是不同的原因：

| 账号权限 | 结果 |
| --- | --- |
| `ALL ON frz_verify.*`（只对自己那个库） | `CREATE DATABASE` 被拒 → `BACKUP_RESTORE_FAILED` |
| 再加全局 `CREATE ON *.*` | 建库成功，但**在临时库里恢复被拒**：`ERROR 1142: DROP command denied to user 'frz_verify' for table 'frz_probe'`——mysqldump 的输出带 `DROP TABLE IF EXISTS`，而 **MySQL 里建库的人不会自动获得该库的权限**（与 PostgreSQL 相反） |
| 再加 `ALL PRIVILEGES ON \`frz\_restore\_%\`.*` | 建库、在临时库里恢复、删临时库三步全通 |

**只有全局 `CREATE` 而没有临时库上的权限时，每次隔离恢复都会在对端留下一个临时库**——
实测留下一份 `frz_restore_frz_verify_mysql_a33a0faf`，而且操作以 `BACKUP_RESTORE_FAILED`
失败（错误信息里指名了那个库并提示手工清理，这一点产品做对了）。

因此**部署要求（写进运维手册的那条）**是：MySQL 的备份账号需要

```sql
GRANT CREATE ON *.* TO 'backup'@'%';                             -- 建临时库
GRANT ALL PRIVILEGES ON `frz\_restore\_%`.* TO 'backup'@'%';      -- 在临时库里恢复 + 删临时库
```

**不需要**给它 `*.*` 上的全权。PostgreSQL 侧不同：那边建库的人自动是属主，因此
`CREATEDB` 就够了（D12 里写的就是这一条，MySQL 侧的要求本轮才补全）。

### 发现 2（harness 侧：我自己的往返断言一直在空转）

**MySQL 里 `||` 是逻辑或，不是字符串拼接**（PostgreSQL 里才是拼接）。`test/dbbackup` 里给
MySQL/MariaDB 写的「内容指纹」表达式因此**永远返回 1**：

```sql
-- 错的（MySQL 里 3 || '|' → 3 OR 0 → 1）
SELECT count(*) || '|' || coalesce(sum(id),0) || ...
```

后果是合约里那条最核心的断言——「备份 → **把表整张删掉** → 原地恢复 → 内容一致」——
退化成「表里有至少一行」，而且**一路绿着通过**。这条只有真实主机才撞得出来：容器里三家
实例一直是同一个常量在比同一个常量。

修法两条，都要留下：

1. 指纹改用 `CONCAT(...)`；修好后重跑 `make verify-db`，三家实例仍然 **12/0**——
   **产品本身没有问题，是测试在空转**。
2. 新增**元断言** `TestFingerprintIsContentSensitive`：造完内容后改一行的值，指纹**必须变**；
   再改回来，指纹必须回到原样。它测的不是产品，而是**夹具的指纹有没有分辨力**——
   「断言测不出东西」比「断言失败」更危险，值得用一条专门的用例钉住。它现在随每个引擎一起跑。

### 重启验证的覆盖范围（2026-09-24，同一台机）

重启后 21 项通过 / 0 项失败）。**要说清覆盖边界**：重启后跑的是 **runtime 那一组**断言

## 23. 2d 设计决定（2026-09-24，实现前冻结）

**范围**（按用户 2026-09-24「按推断，去做 2d」，即第 22 节的推断获得确认）：

- **做**：`prune` 同步用例（只用 `keepLast` / `keepDays`）、保留集合的计算、先标记后删、
  共享 digest 的保护、跳过正在被操作的备份、`--dry-run`、HTTP 端点与 CLI。
- **不做**：**GFS**（停放在 [2026-09-24-future-iterations.md](./2026-09-24-future-iterations.md) 第 2 节）、
  **store-wide 的备份孤儿回收**（理由见本节末）。

### P1：保留集合的判据（只用 `keepLast` / `keepDays`）

```
候选 = 该策略下 Usable() 的备份          （succeeded 且校验没失败）
保留 = 最近 keepLast 份  ∪  完成时刻在 keepDays 之内的
```

两者取**并集**，各自独立成立（与 GFS 的 Q2 一致：一条规则不该把另一条的名额挤掉）。

`keepLast <= 0` = 不按份数保；`keepDays <= 0` = 不按天数保。领域校验要求 `retention`
至少给出一项，因此两者不会同时为 0。

**`keepDays` 按「24 小时 × N」算，不是自然日**：与 1a 制品 GC 的 `olderThan time.Duration`
同源（`internal/application/artifact.go`）。GFS 的日/周/月才需要时区感知的日历语义
（决定 4），`keepDays` 是"多久之内不删"的时长承诺，用流逝时间最不含糊。

**非 `Usable()` 的行既不参与计算、也不被删**——这是 D9 的原话（`Usable()` 的注释里写着
「未完成或校验不一致的对象**不得**进入清理范围」），三条都算：

| 行的状态 | 参与计算？ | 会被 prune 删吗？ |
| --- | --- | --- |
| `pending` / `running`（未完成） | 否 | 否（也没内容可删） |
| `failed` | 否 | 否 |
| `succeeded` 但**校验失败** | 否 | **否** |

最后一行的后果要说清楚：**一份校验失败的备份会一直留在存储里**，占着它的字节，直到有人
显式处理。这看着像浪费，但方向是对的——它是「这份备份有问题」的证据，静默删掉证据比留着
垃圾坏得多。这条已记入停放区第 3 节。

### P2：删除的顺序与动作

1. **先**标记元数据：`status → pruned`，并写一条 `backup.pruned` 审计事件
   （`event_type` 已有，`operation_id` 为 NULL——prune 不是 Operation）。
2. **再**判断该 digest 是否还有未删的引用（见 P3）；没有才删除存储内容。

中断在 1 与 2 之间 → 留下一个无人认领的 blob，而元数据是自洽的（D9 的取舍：宁可留孤儿，
不可留「元数据说在、内容没了」）。

### P3：共享 digest 的保护（跨策略）

删除内容之前必须确认**没有别的未删备份记录**指向同一个 digest。查法仿照 1a 的
`CountArtifactReferences`：新增 `CountBackupReferencesByDigest`，数的是**未被 pruned** 的、
`storage_digest` 相同的行数——**跨策略**数，因为内容寻址是全局按内容去重的。

加密**关闭**时同内容同 digest，这一条就会真的用上；加密默认开启时每块用独立随机 nonce、
同内容不同 digest，因此默认配置下不会共享——**但这条不能靠「默认配置成立」**。

### P4：正在被操作的备份

**判据是「该备份上有未完成的 Operation」（`pending` 或 `running`）**，命中就**跳过并计数**，
不让整批 prune 失败。prune 的语义是「清理该清理的」，一份正在被恢复的备份不该让另外
两百份都留着。结果里给出「跳过 N 份（正在被操作）」，并打 warn 日志。
`BACKUP_IN_USE` 留给「删除被拒绝」这类硬失败，不用于跳过。

> **2026-09-24 实现时修正**：P4 原本写的是「查活跃锁（`ActiveLock`）」。写代码时发现那是
> **错的判据**：资源锁是在 worker **领取**操作时（`ClaimNextPending`）才获取的，不是提交时。
> 因此一份**排队中**（`pending`）的恢复根本拿不到锁——按活跃锁判断会放它过去，prune 删掉
> 它要读的内容，等 worker 领到时恢复只能以「没有对应的存储内容」失败。
> 现在改用 `HasIncompleteOperation`（`status IN ('pending','running')`）——**与
> `CreateOperation` 判定 `LOCK_BUSY` 用的是同一个判据**。这不只是修一个窗口：同一个词
> （「这个资源正被用着」）在仓库里只该有一个定义，两套判据迟早会漂移出第三种行为。

### P5：`--dry-run`

不标记元数据、不删内容，只返回"将要删除"的清单与计数。与制品 GC 的 `GCResult.DryRun` 同形。

### P6：结果结构

```go
type PruneResult struct {
    DryRun     bool
    Policy     string
    Removed    []string     // 已标记为 pruned 的备份 ID
    Skipped    []PruneSkip  // {BackupID, Reason}：正在被操作、内容仍被引用
    Kept       int
    FreedBytes int64
    IgnoredRetention []string // 策略里声明了、而本版本不实现的保留项（见 P7）
    Truncated  bool           // 扫描被上限截断（见 P9）
}
```

### P7：Q6 的落地——策略里声明了 `gfs` 就在**提交期**拒绝

`SavePolicy` 增加一条：`retention.gfs` 的任一项大于 0 → `MANIFEST_INVALID`，消息里写明
「GFS 保留本版本未实现」并指向停放区文档。

**这是本轮唯一改变既有 API 行为的地方，兼容性影响必须记下**：2a 与 2b 都接受并存储过带
`gfs` 的策略，改动之后这类策略**不能再提交**（库里已存在的行不受影响，也不会被删，但下一次
覆盖提交会被拒）。选它的理由与「加密默认开启」同源：把摩擦留在提交期，逼「我要 GFS」成为
一个被写下来的决定，而不是一件悄悄没做的事。

**兜底（覆盖"旧库里已经有 gfs 策略"这一情形）**：`prune` 读到这样的策略时**不静默**——
结果里的 `IgnoredRetention` 带上 `gfs`，并打 warn 日志。

### P8：不进 Operation、不占 resource 锁

`prune` 是**同步**用例（决定 5），与 1a 的制品 GC 一致：不建 Operation、不占 `resource` 锁。
它仍然安全，靠的是两条：候选集合只含**已完成**的行（正在跑的备份状态是 `running`，
天然不在候选里），以及 P4 的跳过。

### P9：扫描范围与截断

新增仓储方法 `ListBackupsForRetention(ctx, policyRef, limit)`：按**完成时刻倒序**取该策略的
备份，**包含非 `succeeded` 的行**——过滤交给领域层的 `Usable()`，这样「谁参与计算」只有
一处判据，也才测得出来。

上限 `maxBackupScan = 5000`。达到上限时 `Truncated = true` 并打 warn 日志：按完成时刻倒序
取，被截断的只能是**更老的**那些，因此截断的方向**保守**（不会多删），但必须说出来。

### 验收标准（2d）

| # | 判据 | 证据类型 |
| --- | --- | --- |
| 1 | 保留集合符合 P1（表驱动：`keepLast` 边界、`keepDays` 边界、并集、非 Usable 行既不参与也不占名额） | 单元测试 |
| 2 | 声明了 `gfs` 的策略在**提交期**被拒（`MANIFEST_INVALID`） | 单元 + 集成 |
| 3 | `prune --dry-run` 不改元数据、不删内容 | 集成 |
| 4 | 真实 prune 只删保留集合之外的 `Usable` 行；先标记后删 | 集成 |
| 5 | 共享 digest 的另一个（**别的策略**的）未删记录仍在时，不删内容 | 集成 |
| 6 | 有未完成 Operation 的备份（排队中或正在跑）被跳过并在结果里报告 | 集成 |
| 7 | 端到端：连备 3 份 → prune 掉 2 份 → 剩下那份仍能 `verify` 且能恢复出正确内容 | 集成 + e2e |
| 8 | `make ci` / `make verify-linux` / `make verify-db` 全绿，回归通过 | 静态 + 全部 |

### 明确不做：store-wide 的备份孤儿回收

D5 说的是「备份自己的孤儿回收**只看备份根**」，那是对**回收动作**的约束，不是「它必须长在
prune 里」。把一次**跨策略**的清扫塞进一个**按策略**的命令，会让 `prune --policy orders`
顺手删掉别的策略留下的残片——那是设计错误（一个命令的爆炸半径必须能从它的名字上看出来）。

**后果必须记下**：prune 在 P2 的两步之间崩溃会留下一个孤儿 blob，而**目前没有回收它的人**。
它应当是一个独立的用例（形如 `backup gc`，与 `artifact gc` 对称），已记入停放区第 3 节。

## 24. 2d 实现记录（2026-09-24）

范围见第 23 节：**只用 `keepLast` / `keepDays` 的 `prune` 与验证链**，不含 GFS（停放在
[2026-09-24-future-iterations.md](./2026-09-24-future-iterations.md) 第 2 节）。

### 逐文件要点

**领域层（`internal/domain/retention.go`）**
- `PlanRetention(policy, backups, now)` 是一个**纯函数**：只依赖策略、备份列表与「现在」。
  保留 = 最近 `keepLast` 份 ∪ 完成时刻在 `keepDays` 之内的；非 `Usable()` 的行**两边都不在**
  （既不参与计算、也不进清理范围，D9）。放在领域层并单独表驱动测试，是因为保留策略是这一块
  里唯一容易「看起来对」的部分——它错了只会表现为某天少了一份备份。
- 排序按完成时刻倒序，**同一时刻按 ID 倒序决胜**：没有决胜键时，同一完成时刻的几份备份在两次
  运行里可能排出不同顺序，「最近 N 份」就指向了不同的一组——而 prune 必须可重放。
- `succeeded` 却没有完成时刻的行**保守地保留**：数据不自洽，而「删掉一份我们说不清它什么时候
  完成的备份」是不可逆的。哪一边错都别往删除那边错。

**持久化（`internal/adapters/sqlite/backup.go`）**
- `ListBackupsForRetention` 按**完成时刻**倒序取该策略的备份，且**含非 `succeeded` 的行**：
  「谁参与保留计算」的判据只有领域层的 `Usable()` 一处，在 SQL 里再写一遍就是第二份会漂移的
  真相（也才测得出来）。
- `CountBackupReferencesByDigest` 数还有多少份**未删除**的备份指着同一个 digest。
- `MarkBackupPruned` 在**一个事务**里改状态并写 `backup.pruned` 审计事件（`operation_id` 留空，
  备份 ID 进 `details`）；行已经不是 `succeeded` 时返回成功且不写审计——prune 必须可重跑。
- `HasIncompleteOperation` 直接复用 `CreateOperation` 判 `LOCK_BUSY` 用的那个助手。

**应用层（`internal/application/backup.go`）**
- `Prune(ctx, policyRef, dryRun)`：一次扫描、一次算「现在」（cutoff 与审计时间同源）、
  逐份处理。三条安全边界都在这一个函数里：只删 `Usable()` 的、有未完成 Operation 的跳过、
  内容仍被引用时只标记不删。
- **先标记、后删内容**（D9）。dry-run **也做引用检查**——报出来的字节数必须是真的会释放的字节数。
- `PruneResult` 把「跳过」和「被忽略的保留项」都带回给调用方，而不是只写日志：运维看到
  「该删 200 份、实际删了 198 份」时，第一个问题就是那两份去哪了。
- `SavePolicy` 增加一条：`retention.gfs` 任何一项大于 0 → `MANIFEST_INVALID`。

**对外（`api/v1/backup.go`、`internal/adapters/httpapi/backup.go`、`internal/adapters/client`、`cmd/opsctl/backup.go`）**
- `POST /api/v1/backups/prune`（`{policy, dryRun}`）与 `opsctl backup prune --policy X [--dry-run]`。
  响应形状与制品 GC 的响应同源（扁平、`emptyIfNil` 处理切片）。
- CLI 的人类可读输出把「跳过」逐条列出来，并在被忽略的保留项、扫描截断时各打一行注意。

### 对规格的补充与偏离

1. **P4 的判据从「查活跃锁」改成「有未完成的 Operation」**（实现时发现的规格缺陷，已就地
   修正第 23 节 P4 并写明理由）：**资源锁是 worker 领取操作时才获取的**，不是提交时。
   因此一份**排队中**的恢复根本拿不到锁——按活跃锁判断会放它过去，prune 删掉它要读的内容，
   等 worker 领到时恢复只能以「没有对应的存储内容」失败。改用 `HasIncompleteOperation`
   之后，prune 判定「这个资源正被用着」与 `CreateOperation` 判定 `LOCK_BUSY` 用的是**同一个
   判据**——同一个词在仓库里只该有一个定义。
2. **`prune` 不做 store-wide 的孤儿回收**（第 23 节末尾有完整理由）：把一次跨策略的清扫塞进
   一个按策略的命令，会让 `prune --policy orders` 顺手删掉别的策略留下的残片。它应当是一个
   独立的用例（形如 `backup gc`），已记入停放区。

### 发现

1. **`prune --dry-run` 与实跑的清单必须逐字一致**，否则它就不是预演。这条写进了集成测试：
   先 dry-run 记下清单，再实跑，两边比对。
2. **「校验失败的备份会永远留在存储里」是 D9 的直接后果**（`Usable()` 既不让它参与计算、
   也不让它进清理范围）。方向是对的——它是「这份备份有问题」的证据，静默删掉证据比留着垃圾
   坏得多——但「占着字节且没有任何东西会回收它」这件事本身该被记下来，已记入停放区第 3 节。
3. **容器 harness 的 `check_backup` 与 `check_prune` 共用同一个备份根**，因此新断言一律看
   **增量**（`prune 之前有几个 blob` → `之后有几个`）而不是绝对数。第一版把绝对数写成 3，
   结果因为前一组留下的那份而失败——这属于 harness 的错，记在这里免得下次再犯。
