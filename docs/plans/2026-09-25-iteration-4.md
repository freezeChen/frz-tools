## 1. 定位与前置

迭代 3 交付的是**单槽部署**：一个应用一个 unit，`current` 符号链接指向当前 release，
换版本时**先停旧的、再起新的**——因此发布期间有一段时间服务是停着的。迭代 4 要的是
路线图第 7 节那句话：**新进程先起来并就绪，再把流量切过去，旧进程排空后才停**。

这两件事在根本上是冲突的，必须先说清楚：

| | 迭代 3（单槽） | 迭代 4（蓝绿） |
| --- | --- | --- |
| unit | 每个应用一个，`ExecStart` 指向 `releases/current` | **每个 slot 一个**（`<app>-blue.service` / `<app>-green.service`） |
| 换版本 | 停旧 → 起新（有中断） | 起新 slot → 就绪 → **切流** → 排空停旧 slot（无中断） |
| 谁在接流量 | `current` 指向谁就是谁 | `applications.serving_slot` + Nginx upstream |
| 回滚 | 把 `current` 切回去、重启 | 把 upstream 切回去、把旧 slot 重新拉起 |

**迭代 3 的语义对「没有声明 slot 的应用」原样保留**：manifest 里不写 `exec.slots` 的应用，
行为与今天完全一致（一个 unit、`current` 链接、先停后起）。蓝绿是**声明式的可选形态**，
不是把所有人拖过去。这样做的代价是两套部署语义同时存在——因此第 4 节把两者的边界
（哪些字段互斥、哪些字段含义随形态变化）写成**校验**，而不是留给文档去解释。

## 3. 关键决策

### D1：蓝绿的形态 = **每 slot 一个 unit + 每 slot 一个端口 + Nginx 切流**

- unit：`<application>-<slot>.service`（**派生**，不允许手写，见 D8）；
- 端口：每个 slot 各声明自己的端口（用户 2026-09-25 拍板，见第 11 节）；
- release 目录：**仍然只有一棵**（`/opt/opsd/apps/<app>/releases/<release-id>`）。制品不可变、
  同一个制品两个 slot 都可能在跑（回滚时尤其如此），因此**不按 slot 各存一份**；
- 每个 slot 有自己的 `current` 指针：`/opt/opsd/apps/<app>/slots/<slot>/current` →
  `../../releases/<release-id>`。**不做成符号链接的符号链接**，而是直接指向 release 目录：
  解析链路越短，出问题时越好查。

代价（写清楚）：一个应用从单槽切成蓝绿时，unit 名会变（`<app>.service` → `<app>-blue.service`），
因此**已经用单槽部署过的应用不能直接改写 manifest 成蓝绿**——那是换部署形态，需要一次
显式的迁移（先把旧 unit `Stop` 掉并 `disable`，再按蓝绿形态 `Prepare`）。本迭代**不做**
自动迁移：迁移脚本与「存量应用怎么过去」列在未验证/后续项里。

### D2：谁在接流量 = `applications.serving_slot`；**对账以 Nginx 为准**

库里的 `serving_slot` 是**运营视图**，Nginx 的 upstream 是**线上事实**。两者可能不一致
（opsd 崩在「写完 include 但还没落库」之间、有人手工改了 Nginx、机器重启后状态丢了）。

规则：**对账以 Nginx 的实际配置为准**，因为那是真正决定请求去哪边的那个东西。因此：

- 受管 include 是**唯一**承载「现在指向哪个 slot」的线上事实（D3）；
- `serving_slot` 是它的镜像，每次切换**先改 include 再落库**（顺序不能反：先落库再改配置，
  中间崩溃会让库说 A、而流量在 B，且没有任何补偿）；
- `app slot` 命令与 reconcile 会**读 include 并与库比对**，不一致时以 include 为准并告警
  （把差异写进审计，而不是悄悄改库）。

### D3：Nginx 受管配置：只写自己的目录，且**必须验证它真的被加载**

- 受管目录：`<nginx.confDir>/frz-managed/<application>.conf`（`confDir` 可配置，默认
  `/etc/nginx`）；
- 内容：一个 `upstream` +（可选）一个 `server`（见 D6），upstream 指向 **serving slot 的端口**；
- **不改写用户主配置**。运维需要在主配置里 include 我们的目录（Ubuntu 默认的
  `include /etc/nginx/conf.d/*.conf;` 若指向该目录则天然满足）；
- `Prepare` 与每次切流前都执行一次检查：`nginx -T`（dump 全部生效配置）的输出里必须能找到
  我们的**受管文件被加载**的证据。**找不到就拒绝切流**并给出明确报错——「配置写对了但没生效」
  是最危险的状态：切流看起来成功了，流量却还在旧版本（或者根本没经过 Nginx）。

### D4：切流序列（每一步失败都要说清楚流量现在在哪）

1. **起新 slot**：`Prepare`（写 unit + 环境文件）+ `Start` 新 slot 的 unit，轮询**新 slot 的**
   就绪目标（复用 3b 的 `waitForReady`，超时预算取 `health.startTimeoutSeconds`）；
2. **生成候选 include**：写临时文件（不覆盖线上那份），upstream 指向新 slot 的端口；
3. **校验**：`nginx -t -c <主配置>`（校验的是**候选配置**——把它临时装到位再校验，
   或在临时目录里整份 dump 校验，见实现记录）；失败 → 拒绝切流，**流量未动**；
4. **原子替换**：`rename` 受管文件（与 `current` 切换同一个套路：先写
   `<app>.conf.tmp` 再 rename）；
5. **reload**：`nginx -s reload`（graceful：旧 worker 排空在途请求）。失败 → 把第 4 步替换
   掉的文件**换回原来那份**并再 reload 一次（如果连回滚 reload 都失败，报
   `NGINX_RELOAD_FAILED` 并要求人工介入——**不报「已回滚」**）；
6. **观察窗口**：按 `nginx.observationSeconds`（默认 30）**在 Operation 内**串行采样
   （间隔与 3b 一致，200ms；采样项：新 slot 的就绪探活 + `systemctl show -p NRestarts`
   的增量）。窗口内发现就绪转坏或进程在反复重启 → **按失败处理**（回到第 3 步之前的语义：
   切回 upstream、停新 slot）；
7. **promote**：落库 `serving_slot` 与 release 状态（`active`），旧 slot 的 release 转
   `superseded`；
8. **排空停旧 slot**：等 `nginx.drainSeconds`（默认 5，覆盖 reload 后旧 worker 处理在途请求的
   时间）再 `Stop` 旧 slot 的 unit。**只停进程，不删目录**——回滚就是把它重新拉起来。

### D5：失败语义沿用 3c 的三态，但「什么都没动」在蓝绿里要重新定义

3c 定下的规则：`DEPLOY_ROLLED_BACK` 只说一件事——**改动过线上并把它撤销了**；什么都没动时
返回原因码。蓝绿里的对应关系：

| 失败点 | 线上流量 | 结论 |
| --- | --- | --- |
| 新 slot 起不来 / 不就绪（第 1 步） | 未动 | 原因码（`RUNTIME_NOT_READY` 等），并说明「流量未受影响」 |
| 候选配置校验失败（第 3 步） | 未动 | `NGINX_CONFIG_INVALID` |
| reload 失败（第 5 步） | 动过（配置已替换） | 换回 + 再 reload 成功 → `DEPLOY_ROLLED_BACK`；换回也失败 → 原码 + 「需要人工介入，流量可能在旧 slot 或已中断」 |
| 观察窗口内退化（第 6 步） | 动过（流量已切到新 slot） | 切回旧 slot → `DEPLOY_ROLLED_BACK` |

新 slot 的进程在失败后一律 `Stop` 并撤掉它的 `current` 指针（与 3b 的
`teardownFirstDeploy` 同理：留着指针指着马上要删的目录，会让「现在跑的是哪个版本」指向
不存在的东西）。

### D6：manifest 只声明**事实**，不发明模板语法

`exec.slots.<slot>` 里写的是「这个 slot 听哪个端口、就绪怎么探、应用怎么知道自己的端口」，
都是运维本来就要决定的事：

```yaml
exec:
  argv: [bin/server]
  runUser: orders-api
  slots:
    blue:
      ports: [18081]
      readiness: {type: tcp, target: "127.0.0.1:18081"}
      environment: {ORDERS_HTTP_ADDR: "127.0.0.1:18081"}
    green:
      ports: [18082]
      readiness: {type: tcp, target: "127.0.0.1:18082"}
      environment: {ORDERS_HTTP_ADDR: "127.0.0.1:18082"}
```

- **应用怎么知道自己的端口**：用**已有的 `environment` 机制**（每个 slot 各写一份环境文件），
  变量名由运维定（`ORDERS_HTTP_ADDR`、`SERVER_PORT`、`PORT` 都行——取决于应用）。
  工具**不**发明 `FRZ_SLOT_PORT` 之类的注入变量：那会让「应用必须配合某个魔法名字」变成
  隐式契约，而这里本可以显式写清楚。代价是每个 slot 多两行——值得。
- **就绪目标按 slot 写**：端口不同，探活目标当然不同。写全比自动把 `health.readiness` 里的
  端口替换成 slot 端口要诚实（后者是「猜运维的意思」）。
- `health.readiness` 在蓝绿应用上**不再使用**（由每个 slot 自己声明）；同时给出两者是
  `MANIFEST_CONFLICT`，还是允许 `health` 只写 `startTimeoutSeconds`/`stopTimeoutSeconds`？
  **决定**：`health` 段退化为「只放两个超时」（`readiness` 由 slot 提供），
  因此在蓝绿应用上 `health.readiness` 若同时出现 → `MANIFEST_INVALID`，报错说清
  「就绪目标请写在 `exec.slots.<slot>.readiness`」。

### D7：`nginx` 段：对外入口也是**声明**出来的

```yaml
nginx:
  listen: 8080                      # 必填：对外端口（由 Nginx 监听）
  serverName: orders.example.com    # 可选：server_name
  upstreamName: orders-api          # 可选：默认按应用名派生，见下
  observationSeconds: 30            # 可选
  drainSeconds: 5                   # 可选
```

- upstream 名默认 `frz_<application>`（下划线：nginx 的 upstream 名里连字符可用但不在
  所有位置都友好，且这个前缀能把「我们生成的名字」与用户自己的区分开）；
- 声明了 `nginx` 段但主机上没有可用的 nginx（二进制或 `nginx.confDir`）→ `RUNTIME_UNSUPPORTED`，
  并且**在 Prepare 阶段就失败**，而不是切流时才发现；
- 没声明 `exec.slots` 却声明了 `nginx` 段 → `MANIFEST_INVALID`（Nginx 段只服务蓝绿）。

### D8：派生出来的东西不许手写

- unit 名：`<application>-<slot>.service`（蓝绿应用不得写 `systemd.unitName`）；
- `current` 指针：`/opt/opsd/apps/<app>/slots/<slot>/current`；
- 受管 Nginx 文件：`<confDir>/frz-managed/<application>.conf`；
- 环境文件：`/etc/opsd/apps/<app>.<slot>.env`（单槽应用仍是 `<app>.env`）。

理由与 1c「路径约定的唯一来源在 domain」同一条：**派生规则只能有一处**。蓝绿应用若手写了
unit 名，就会出现「工具按 slot 生成、运维按自己的名字写」两套名字，而 systemd 的 enable/
stop/status 全都要用那个名字。

## 4. manifest 增量与校验

```yaml
exec:
  ports: [18081]          # 单槽形态（与今天一致）
  slots:                  # 蓝绿形态（新增，可选）
    blue:  {ports: [...], readiness: {...}, environment: {...}}
    green: {ports: [...], readiness: {...}, environment: {...}}
nginx:                    # 蓝绿形态配套（新增，可选）
  listen: 8080
```

校验（全部 `MANIFEST_INVALID`，除注明外）：

| 规则 | 说明 |
| --- | --- |
| `exec.slots` 的键只能是 `blue` / `green`（与 `domain.Slot` 枚举同源） | 拼错即错 |
| 两个 slot **都必须给**，且 `ports` 非空 | 「只有一个 slot」不是蓝绿 |
| 两个 slot 的端口不得相交 | 相交意味着两个进程抢同一个端口，切流必然失败 |
| `exec.slots` 与 `exec.ports` 互斥 | 一个是单槽语义、一个是蓝绿语义，同时给必然是写错了 |
| `exec.slots` 与 `systemd.unitName` 互斥 | 见 D8 |
| `exec.slots` 与 `health.readiness` 互斥（`MANIFEST_INVALID`） | 见 D6 |
| 每个 slot 的 `readiness.type` 仍是 `tcp`/`http`，target 形态按 `health.readiness` 的既有规则校验 | 复用现有校验，不复制 |
| `nginx` 段必须与 `exec.slots` 同时出现；`listen` 必填且 1–65535，且不与两个 slot 的端口相交 | 对外端口与 internal 端口撞上必然出事 |
| `observationSeconds` ∈ [0, 3600]，`drainSeconds` ∈ [0, 300] | 0 表示不观察 / 不等待 |
| 蓝绿应用仍可写 `release.keepLast` | 保留策略与形态无关 |

**兼容性**：以上全是**同一 `apiVersion` 内新增的可选字段**，因此不改 `apiVersion`。
`exec.slots` 与 `nginx` 段都没出现的 manifest，解码与校验路径与迭代 3 完全一致
（新增校验只在字段出现时生效）——这一条要有回归测试钉住。

## 5. 数据表变更（迁移 `0010`）

```sql
-- releases：一次部署落在哪个 slot。NULL = 单槽形态（迭代 3 的既有语义）。
ALTER TABLE releases ADD COLUMN slot TEXT;

-- applications：现在哪一侧在接流量。NULL = 单槽形态。
-- **以 Nginx 的实际配置为准，这一列是它的镜像**（见 D2）。
ALTER TABLE applications ADD COLUMN serving_slot TEXT;

-- 每个 slot 的运营视图：它现在跑哪个 release、什么时候切的。
CREATE TABLE application_slots (
    application_id TEXT NOT NULL REFERENCES applications (id),
    slot           TEXT NOT NULL,
    release_id     TEXT,
    state          TEXT NOT NULL,          -- serving | standby | draining | stopped | failed
    switched_at    TEXT,
    updated_at     TEXT NOT NULL,
    PRIMARY KEY (application_id, slot)
);
```

release 状态机扩展（`internal/domain/release.go`）：**只加一个 `standby`**。

```
created → deploying → {standby, active, failed}
standby → {active, superseded, failed}
active → superseded
superseded → active            -- 回滚：旧的又被切回来了
任何状态 → removed             -- 保留策略清理（仍以 current / 任何 slot 指针为界）
```

- `standby`：起来了、就绪了，但**没接流量**（观察窗口内的新 slot 就是这个状态）；
- **`active` 的含义扩成「正在接流量」，不为蓝绿另立一个 `serving`**：单槽应用里
  「`current` 指向它」与蓝绿里「`serving_slot` 指向它所在的 slot」是同一件事——
  一个应用当前正在对外服务的那个版本。两个名字表达同一个概念，迟早会在某处漂移
  （`ActiveRelease`、`Rollbackable`、保留策略都要各判一次）。
  `active` 的文档注释随之改写成「正在接流量」，而不是「`current` 指向它」。
- `Rollbackable()` 仍然是 `active || superseded`，**`standby` 不进回滚目标**：
  它是一次还没成功的部署留下的半成品，回滚到它等于回滚到一个从没接过流量的版本。

**兼容性**：`ADD COLUMN` 带默认 NULL，既有行语义不变；`application_slots` 是空表起步。
迭代 3 的单槽流程**不写这两列**，因此「同一个库同时跑两种形态的应用」是允许的。

## 6. Nginx 受管配置的形态

```nginx
# 本文件由 opsd 生成，请勿手工编辑；由 <application>-<slot>.service 的部署流程维护。
# 现在指向：<slot>（release <release-id>，版本 <version>）
upstream frz_orders-api {
    server 127.0.0.1:18082;
    keepalive 16;
}

server {
    listen 8080;
    server_name orders.example.com;
    location / {
        proxy_pass http://frz_orders-api;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        client_max_body_size 1m;
        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
    }
}
```

**头注释里写「现在指向谁」**是刻意的：出问题时运维第一眼要看的那个事实，就在文件开头
（与 unit 头注释记录档位/版本同一个理由）。

## 7. API 与 CLI

| 命令 | 说明 |
| --- | --- |
| `opsctl app deploy` | 蓝绿应用：走第 6 节的序列。单槽应用：行为不变 |
| `opsctl app rollback [--to <version>]` | 蓝绿应用：把 upstream 切回目标版本所在的 slot（必要时先把它拉起来） |
| `opsctl app slot list --app <app>` | 两个 slot 的状态、release、端口、是否在接流量（human + `--json`） |
| `opsctl app slot history --app <app>` | 切换时间线（谁在什么时候切到哪个 release） |
| `GET /api/v1/applications/{id}/slots` | `slot list` 的 HTTP 形态 |

`app deploy` 的响应里增加 `slot`（本次落到哪个 slot）与 `switching`（是否发生了切流）。

## 8. 错误码与退出码增量

| 错误码 | HTTP | 退出码 | 含义 |
| --- | --- | --- | --- |
| `NGINX_CONFIG_INVALID` | 409 | 31 | 候选配置没通过 `nginx -t`，或受管文件没有被主配置加载 → **拒绝切流，流量未动** |
| `NGINX_RELOAD_FAILED` | 409 | 32 | reload 失败且换回原配置也没成功 → 流量状态不确定，需要人工介入 |

两者都**不进** 1d 的重试白名单：配置问题重试多少次还是配置问题。

## 9. 兼容性与迁移影响

- **manifest**：新增可选字段，`apiVersion` 不变；没有 slot 的 manifest 行为不变（有回归测试）。
- **数据表**：迁移 `0010` 只有 `ADD COLUMN` 与一张新表，既有数据语义不变。
- **错误码**：新增两个（第 8 节），已登记进 `api/v1` 的映射表与本文档。
- **已有单槽应用切蓝绿**：会换 unit 名与指针布局，**本迭代不提供自动迁移**，
  列为未验证/后续项（第 10 节）。
- **`make verify-linux` 的断言数**：4b 起容器镜像要装 nginx（Dockerfile 增一行），
  断言数会增长——以脚本运行时打印的数字为准。

## 10. 验收标准

1. 蓝绿应用的 manifest 通过严格校验；把 `exec.slots` 与 `exec.ports`、`systemd.unitName`、
   `health.readiness` 同时写会被 `MANIFEST_INVALID` 拒绝（含「端口相交」那条）。
2. **发布期间服务不中断**：容器里用 curl 以固定间隔打 Nginx 的对外端口，整个过程（含切流）
   **零失败请求**，且响应里的版本号从旧版切到新版**【Linux 容器】**。
3. 新 slot 起不来 / 不就绪时：流量**一直**在旧 slot，Operation 报原因码且说明流量未受影响。
4. `nginx -t` 失败时拒绝切流；受管文件没被主配置加载时同样拒绝（并给出可操作的报错）。
5. reload 失败时换回原配置并报告 `DEPLOY_ROLLED_BACK`；换回也失败时报
   「需要人工介入」且**不**报已回滚。
6. 观察窗口内新版本退化 → 自动切回旧 slot、报 `DEPLOY_ROLLED_BACK`、新 slot 被停且不留
   `current` 指针。
7. `app rollback` 能把流量切回上一个可回滚版本，且**连配置一起回滚**（沿用 3b 的按 release 版本化）。
8. opsd 重启后 `app slot list` 报出的 `serving_slot` 与 Nginx 实际配置一致（reconcile）。
9. 单槽应用（未声明 slots）的既有行为与断言全部不变：`make verify-linux` 原有断言回归通过。
10. `make ci` / `make verify-linux` 全绿；真机上（legacy 档 CentOS 7，若 nginx 可装）跑一轮。

## 11. 已冻结的决定（2026-09-25 用户拍板）

1. **切流机制 = Nginx 蓝绿**（按路线图第 7 节）。另两个选项「先不做蓝绿只做观察与回滚」
   与「两套按应用可选」都被否掉——后者尤其会造成「没声明时走哪条」的模糊地带。
2. **两个 slot 各自显式声明端口**（不做基准 + 偏移的魔数，也不做环境变量注入）。
3. **观察窗口 + 手动回滚**。自动回滚（窗口内超阈值自动切回）**本迭代不做**：
   真正的「错误率」要读 Nginx 日志、要定阈值，而阈值定错的自动切流比不切更危险。
   窗口内只采样**确定性的事实**（就绪是否还通过、进程是否在反复重启），发现退化按失败处理。

## 12. 未验证内容（规格阶段就写明）

- **已有单槽应用迁移到蓝绿**：unit 名与指针布局都变，本迭代不做自动迁移，也没有手工迁移的
  演练记录。
- **自动回滚**：见第 11 节第 3 条，不做。
- **错误率 / 5xx 峰值**：路线图第 7 节的验收标准里提到「以压测和故障注入验证发布期间无预期
  5xx 峰值」。本迭代能证明的是「切流期间零失败请求」（容器里用 curl 打），**不是**压测结论；
  压测与故障注入记为未验证。
- **多主机 / Nginx 与应用不在同一台机器**：属迭代 5，本迭代假设 Nginx 与 opsd 同机。
- **Nginx 之外的入口（HAProxy、云 LB）**：不做。

## 13. 4a 实现记录（2026-09-25）

范围见第 2 节：slot 进入领域与数据层。**不碰 systemd、不碰 Nginx、不碰部署流程**——
这一片要能在没有 systemd 的机器上用单元测试钉死。

### 逐文件要点

**领域（`internal/domain/slot.go`，新增）**
- `Slot`（`blue`/`green`）、`Slots`（**顺序固定的数组**，不是 map：遍历顺序不该随 map 漂移）、
  `ParseSlot`（只忽略大小写与空白，不做「猜一个最接近的」）；
- `SpecSlot`（端口 / 就绪 / 槽位自己的环境）、`SpecNginx`（对外端口、serverName、upstreamName、
  观察窗口、排空时间）、`Configured()`（`Listen > 0`）；
- **派生出来的路径与名字**：`SlotDir` / `SlotCurrentDir` / `SlotCurrentLinkTarget` /
  `SlotEnvFilePath` / `SlotSecretsEnvFilePath` / `SlotSecretsDir` / `SlotUnitName` /
  `UpstreamName` / `ManagedNginxDir` / `ManagedNginxFile`——与 1c 起就有的
  `ReleaseDir` / `EnvFilePath` / `UnitPath` 同一条纪律：**派生规则只能有一处**；
- `ApplicationSpec` 上的便捷方法：`BlueGreen` / `SlotsFor` / `SlotOf` / `SlotReadiness` /
  `SlotPorts` / `SlotUnitName` / `SlotEnvironment`（**合并** `exec.environment` 与槽位环境，
  同名时槽位优先，且只在这里合并一次）；
- 校验：`validateSlots`（两个槽位必须都给、键合法、端口非空且不越界且**不得相交**、
  槽位就绪合法、槽位环境名合法且不与 `secretEnvironment` 撞键）与 `SpecNginx.validate`
  （对外端口与槽位端口不得相交、serverName / upstreamName 的字符集、观察窗口与排空时间的范围）；
- `validateReadiness` **从 `SpecHealth.validate` 里抽出来**，槽位与单槽共用一份：
  复制一份规则出来，漂移的表现会是「单槽能过、蓝绿过不了」这种解释不清的差异。

**领域（`internal/domain/appspec.go`）**
- `SpecExec` 加 `Slots`、`ApplicationSpec` 加 `Nginx`（都是新增可选字段，`apiVersion` 不变）；
- `validateBlueGreen()` 放在**跨段**的位置：unit 名在 `Systemd` 段、就绪在 `Health` 段、
  单槽端口在 `Exec` 段，而它们与槽位的关系只有在这里才同时看得见。它负责四条互斥：
  `slots` ↔ `ports`、`slots` ↔ `systemd.unitName`、`slots` ↔ `health.readiness`、
  以及「蓝绿必须有 nginx 段 / 有 nginx 段必须是蓝绿」；
- `SpecHealth.validate(blueGreen bool)`：蓝绿应用**跳过**共享 readiness 的校验——
  那个字段在蓝绿里本就该为空，对一份「本该为空」的字段提要求只会让人以为要填两份。

**领域（`internal/domain/release.go`）**
- `ReleaseStatus` 只加一个 `ReleaseStandby`（起来了、就绪了、**没接流量**）；
- `SlotState`（`serving`/`standby`/`draining`/`stopped`/`failed`）与 `ApplicationSlot`：
  它是**槽位**的状态，与 release 状态是两个层次——同一个槽位先后跑过很多 release，
  而槽位状态只有这五种；
- `Release` 加 `Slot` 字段（**空 = 单槽形态**）。

**数据层（`migrations/0010_slots.sql`、`internal/adapters/sqlite/slot.go`）**
- 两处 `ADD COLUMN`（`releases.slot`、`applications.serving_slot`，NULL = 单槽形态）+
  `application_slots` 表（复合主键，空表起步）；
- `SetReleaseSlot` / `PutApplicationSlot` / `ApplicationSlots` / `SetServingSlot` / `ServingSlot`；
- `releaseColumns` 这个共享列清单加上 `COALESCE(slot, '')`，`scanRelease` 同步——
  列清单集中一处就是为了让「加了一处、忘了另一处」不可能发生；
- `PutApplicationSlot` 的 upsert 直接以复合主键为冲突目标：**这张表的两个主键列都是
  NOT NULL**，因此 `ON CONFLICT` 一定触发（与 `application_specs` 那次不同，见 0009 的注释）；
- `switched_at` 用 `COALESCE(excluded.switched_at, application_slots.switched_at)`：
  传 nil 表示「这次动作没切流量」，**保留**原来那个时间，而不是抹成 NULL。

**manifest（`internal/adapters/manifest/manifest.go`）**
- `wireExec.Slots` / `wireSlot` / `wireNginx`（观察窗口与排空时间用**指针**）；
- `convertSlots`（槽位名原样转过去，合法性交给 domain 的校验——一处规则一处报错）、
  `convertNginx`（默认值在**这一层**补，见下）。

### 对规格的补充与偏离

1. **`active` 的含义扩成「正在接流量」，不为蓝绿另立 `serving`**（规格原本写了 `serving`）。
   单槽的「`current` 指向它」与蓝绿的「`serving_slot` 所在槽位跑着它」是同一个概念；
   两个名字会让 `ActiveRelease` / `Rollbackable` / 保留策略三处都要各判一次，进而漂移。
   规格第 5 节已就地改写。
2. **nginx 的默认值在 manifest 层补**（`convertNginx`），不在 `domain.applyDefaults` 里。
   理由：`observationSeconds: 0` 是**显式不观察**，而「没写」要走默认的 30 秒——
   domain 的 `int` 分不出这两件事，在 `applyDefaults` 里补默认值会让「关掉观察」永远做不到。
   默认值本身仍取自 domain 的常量（同一个数字只有一处定义）。
3. **槽位环境与 `exec.environment` 合并且局部覆盖全局**：一个槽位要改的只有端口那一项，
   其余（`GOMEMLIMIT` 之类）与另一个槽位相同，让运维抄两遍没有意义。与
   `secretEnvironment` 撞键仍然报 `MANIFEST_CONFLICT`（与既有的 env/secret 撞键规则同源）。

### 发现

1. **「显式 0」与「没写」的区别，必须在能表达它的那一层处理。** 我最初把观察窗口的默认值
   放在 `applyDefaults` 里，于是 `observationSeconds: 0` 会被改写成 30——**一个合法且有
   意义的取值（不观察）被默认值吃掉了**。修法不是在 domain 加一个 `bool`，而是把默认值挪到
   wire 那一层：那里本来就有指针，本来就能分清。
2. **「测试没跑」看起来与「测试通过」几乎一样。** 我把一个 Go 测试文件写到了错误的路径
   （少了仓库上层目录），`go test -run 'BlueGreen|...'` 的输出是
   `ok ... [no tests to run]`——**退出码 0、绿色的 ok**。发现它靠的是去看 `-v` 的用例列表，
   而不是靠命令成不成功。与「MySQL 里 `||` 让指纹永远是 1」是同一类问题的两个面：
   **断言/用例根本没执行，比执行了失败更危险。**
3. **python 的字符串替换没匹配上时是静默成功的。** 给 `releaseColumns` 加列那一步，
   我按记忆写的旧文本与文件里的实际内容不一致（文件里是 `COALESCE(directory, '')` 那一版），
   替换什么都没做——直到 `scanRelease` 的 Scan 参数个数不匹配才以「expected 13 destination
   arguments in Scan, not 14」暴露出来。此后所有脚本替换都带 `assert count == 1`。
