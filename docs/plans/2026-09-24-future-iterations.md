## 2. GFS 保留策略（2026-09-24 从迭代 2d 移出）

### 2.1 它是什么

GFS = Grandfather-Father-Son，备份保留的经典三代策略：**近的密、远的疏**。一份备份只要被
任意一条规则保下来就留着，于是「每天备一次、连跑半年」得到的不是 180 份，而是大约
`daily + weekly + monthly` 份——近一周每天都能回到，一个月内每周有一份，半年内每月有一份。

| 档 | 粒度 | 回答的问题 |
| --- | --- | --- |
| son（`gfs.daily`） | 天 | 「昨天下午那批数据还在吗」 |
| father（`gfs.weekly`） | ISO 周 | 「上周三出问题前是什么状态」 |
| grandfather（`gfs.monthly`） | 自然月 | 「上季度末的基线长什么样」 |

### 2.2 为什么现在不做

- **更急的那一半是 `keepLast` / `keepDays`**：今天**什么都没有 prune**，备份会无限增长。
  「最近 14 份永远在」这一条就挡住了无限增长，而 GFS 解决的是「很久以前也要有几份」——
  那是备份攒多了之后才痛的问题。
- GFS 有一组**必须先定死**的语义问题（见 2.4）。定它们需要的是决策时间，而不是实现时间；
  在没有真实需求压着的时候定，容易定成猜的那一套。

**取用条件**：备份量开始让人担心磁盘（`keepLast`/`keepDays` 已经不够），或者用户明确要求
「月度基线」这类能力。

> **2026-09-24 更新**：2d 已经落地，`prune` 现在只按 `keepLast` / `keepDays` 清理。因此
> 「备份无限增长」这个问题已经被挡住了；GFS 现在解决的是剩下那一半——**很久以前也要留几份**。

### 2.3 已经冻结、不用再定的部分

| 事项 | 结论 | 出处 |
| --- | --- | --- |
| 保留策略归属 | 属于**应用层**，**不**抽象进适配器——否则每个适配器各实现一遍，必然漂移成几套语义 | 迭代 2 规格 D3 |
| 谁参与保留计算 | 只有 `succeeded` **且**校验没失败的备份；未完成/失败的行**不参与**，也**不占** `keepLast` 名额 | D9，判据在 `internal/domain/backup.go` 的 `Usable()` |
| 标签怎么算 | 按**完成时刻**落在哪一天/哪一周/哪一月；周按 **ISO 8601**（周一为第一天），月按自然月；**时区取计划声明的时区**，不依赖主机本地时区 | 决定 4 |
| 标签何时算 | 备份**完成时**算好并存进 `backups.labels_json`（不是删的时候现算），因此后来改策略的时区不会追溯改写历史标签 | `migrations/0006_backups.sql` |
| `prune` 同步还是异步 | **同步**，与 1a 的制品 GC 一致；数量或删除量超过阈值时打一条 warn 日志 | 决定 5 |
| 删除顺序 | **先标记元数据、后删内容**：中断时最坏留下一个无主的 blob（可由孤儿回收处理），不会留下「元数据说在、内容没了」 | D9 |
| 备份自己的孤儿回收 | 只扫**备份根**，不得顺带清理制品根 | D5 |

已经就位的脚手架：`retention.keepLast/keepDays/gfs.*` 的模型与严格解码（2a）、
`backups.labels_json` 列与 `ix_backups_policy_finished`（按策略+完成时间倒序）、
`ix_backups_digest`（按 digest 查引用）、`pruned` 状态与 `backup.pruned` 审计事件的词汇。

### 2.4 开工前必须定死的六个问题（含推荐值）

#### Q1 同一个周期里留哪一份？

| 选项 | 含义 |
| --- | --- |
| **A（推荐）** | 该周期内**最后完成**的一份 |
| B | 最早完成的一份（周期开始时的状态） |
| C | 都留——等于没有周期语义 |

**推荐 A。** GFS 要回答的是「回到那个周期的某个状态」，而周期结束时的状态是那个周期里
最新、最完整的；B 的「基线」价值可以由更长的周期覆盖（weekly/monthly 的 A），而 A 不可替代。
A 也与主流工具一致，运维不必重新学一套语义。**已核对 restic 的原文**（`restic forget`）：
「for the last `n` days **which have one or more snapshots**, keep only the **most recent**
one for each day」——daily / weekly / monthly 三条都是「留该周期**最近**的一份」，
且它把周定义为**周一 00:00 到周日 23:59**，与本仓库决定 4 的 ISO 8601 一致。

**顺带必须一起定的：周期是「怎么数」的。** 上面那句原文里藏着第二个语义问题——
「最近 n 天」数的是**有备份的那些天**，不是最近 n 个自然日。两者差在"某天没备份"时：

| 数法 | `daily: 7` 的含义 | 后果 |
| --- | --- | --- |
| **A（推荐，与 restic 一致）** | 最近 **7 个有备份的**日子各留一份 | 连续 7 天没跑备份 → 那 7 份较早的仍然留着，不会因为"过期"被删光 |
| B | 最近 7 个**自然日**内有备份就留 | 一旦连着几天没跑，窗口里就只剩少数几份，甚至一份不剩 |

**推荐 A**：`daily: 7` 是运维给"我要能回到最近 7 个不同日子"的承诺，而自然日数法会让
「停机三天」这种事顺手把保留量砍掉一半——那不是用户的意图。这条与 Q3（`keepDays` 是硬下限）
是配套的：一个是「按份数保」，一个是「按天数保」，两者都不该被"没跑到"惩罚。

#### Q2 `keepLast` 与 GFS 是并集吗？

**推荐并集**：一份备份只要被任意一条规则保下来就留着。`keepLast` 保证「最近 N 份永远在」，
GFS 保证「每个周期的代表永远在」，两者语义正交。
**要避免的写法**是「先满足 keepLast 再按 GFS 补」（或反之）——那会让一条规则把另一条的名额挤掉。

#### Q3 `keepDays` 是硬下限吗？

**推荐是**：完成时刻在 N 天之内的一律不删，哪怕所有 GFS 规则都说可删。
`keepDays` 的字面承诺就是「留 N 天」，把它降级成「建议」的后果是：用户在一次 prune 之后
发现三天前那份没了，而策略里明明写着 30 天。

#### Q4 同一个 digest 被多份备份共享时怎么删？

**推荐：删 blob 之前先确认没有别的备份记录指向它**（`ix_backups_digest` 就是为这个建的）。
两种场景都会出现：加密**关闭**时内容寻址会去重（同内容同 digest）；同一份备份的记录被重试重建。
做法是先算出「本轮保留集合」，再对每个待删记录检查它的 `storage_digest` 是否仍在保留集合里
（或仍被任何未删记录引用），是则**只改状态、不删 blob**。
（加密开启时每块用独立随机 nonce，同内容不同 digest，因此默认配置下不会共享——但这条不能靠
「默认配置」成立。）

#### Q5 正在被恢复/校验的备份怎么办？

**推荐：跳过并计数，不让整批 prune 失败。** prune 的语义是「清理该清理的」，一份正在被用的
备份不该让另外两百份都留着。结果里给出「跳过 N 份（正在被操作）」，并打 warn 日志。
实现上要查一次活跃操作（`ActiveLock`，或按 `resource` 查未完成的 Operation）。
规格里那个 `BACKUP_IN_USE` 错误码（409）留给「删除被拒绝」这类硬失败，不用于跳过。

#### Q6 策略里声明了 `retention.gfs`、而本版本不实现时，怎么办？

**这条必须在 prune 落地的那一步定死，否则会出现「静默忽略」**：策略里写着每月留 6 份，
prune 完全不看它，而运维以为生效了——这正是本仓库最不能接受的一类失败。

| 选项 | 评价 |
| --- | --- |
| **A（推荐）** | 提交期**拒绝**（`MANIFEST_INVALID`）：声明了本版本不做的事就不许存 |
| B | 接受，但在 prune 结果里明确报告「策略声明了 gfs，本版本忽略它」 |
| C | 接受并静默忽略 | 不可接受：与「加密绝不静默降级」同一条道理 |

**推荐 A**，理由与「加密默认开启」同源：把这个摩擦留在**提交期**，逼「我要 GFS」成为一个
被写下来的决定，而不是一件悄悄没做的事。

> **2026-09-24 落地**：2d 实现时按选项 A 做了——`SavePolicy` 现在拒绝声明了 `gfs` 的策略
> （`MANIFEST_INVALID`，消息指向本文档）；对**旧库里已经存在**的 gfs 策略，`prune` 的结果里
> 会带上 `ignoredRetention: ["gfs"]` 并打 warn 日志（选项 B 的兜底）。见迭代 2 文档第 24 节。
**兼容性影响（必须先记）**：2a/2b 已经接受并存储带 `gfs` 的策略，改成拒绝意味着这类策略
**不能再提交**（已存在的行不受影响，但下一次覆盖提交会被拒）。按仓库约定，改这一条要先更新
迭代 2 文档并记录兼容性影响。若判定兼容成本过高，**B 是可接受的折中**，但必须真的把这句话
打到调用方看得见的地方（prune 的返回里），而不是只写日志。
