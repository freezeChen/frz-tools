# 迭代 5：远程、多主机与生产加固（规格）

> 路线图第 8 节。前四个迭代把**单机闭环**做完了（制品 → 部署/蓝绿 → 备份/恢复 → 观察与对账），
> 迭代 5 要把它从「一台机器上的工具」变成「一群机器上的工具」。
>
> 本文是规格；实现记录与验证记录在文末追加。**开工前已由用户拍板四条决定**，见第 10 节。
> 里程碑按 5a → 5b → 5c → 5d 推进，每一片单独可验证、单独可停。

## 1. 定位与前置

已具备（前四个迭代的产物，全部有容器/真机证据）：

- 目标机上的 `opsd` 是一个**完整的执行者**：它持有本机 sqlite、资源锁、Operation 状态机、
  重试与退避、审计与日志、release 目录、systemd unit、Nginx 受管配置、备份与恢复。
- `opsctl` 是本机客户端，通过 Unix socket 上的 HTTP/JSON `api/v1` 与它通信。
- `Host` / `Environment` 在 1c 起就有记录，但**只承载身份与标签**：`address` 为空表示本机，
  域里的注释明确写着「远程主机、SSH 与 mTLS 属于迭代 5，届时才把这些字段变成真正的连接参数」
  （`internal/domain/host.go`）。

缺的是什么（这就是迭代 5 要补的）：

- `opsd` **只监听 Unix socket**，访问控制只有 socket 文件模式一层：能连上就能做任何事。
- 「谁做的」今天来自请求体里的 `createdBy`（**调用方自报**）。这在 socket 形态下是可信的
  （能连上 socket 本身就等于本地运维），**一旦把端口开出去就变成可冒充的输入**。
- 没有「一次看多台」的能力，也没有主机可达性的概念。

## 3. 关键决策（5a）

### D1：远程形态 = **每台目标机装 opsd（agent）**，中央只做编排与汇总

目标机上的 `opsd` 是**唯一**的执行者：锁、幂等、审计、日志、重试、状态机、对账全都在它那里。
中央（`opsctl`）只做两件事：连过去、把看到的汇总成视图。

**为什么否决 SSH 执行器形态**（路线图给的另一个选项）：SSH 形态下目标机上没有库、没有锁，
于是「同一 resource 任意时刻最多一个未完成 Operation」这条不变量会从「一台机器」退化成
「一次连接」——两个并发连接可以同时往同一个 release 目录上写，而**没有任何东西会拦住它们**。
release 目录、unit 文件、Nginx 配置都要隔着 ssh 写，也就都没了「写之前先在同一把锁下检查」的
地方。这是**静默降级**：命令会成功，而保证没了。本仓库在同类问题上的纪律是一致的
（宁可明确报 `RUNTIME_UNSUPPORTED`，也不让 `proc` 假适配器在生产假装能用）。

代价（写清楚）：每台目标机要装并升级 `opsd`；升级顺序在 5b 的规格里要单独说（先升 `opsd`
还是先升 `opsctl`）。

### D2：传输 = **mTLS 双向证书**；`opsd` 默认**不听**远程端口

- 配置里**没有 `remote.listen` 就完全不听 TCP**：默认形态与今天逐字节一致（只有 Unix socket）。
  这与 Nginx 适配器「可以缺席，但缺席必须有明确说法」是同一条：能力是显式声明的。
- **TLS 最低版本 1.2**，不用 1.3。理由很实际：legacy 档目标机是 CentOS 7，
  它的 `openssl 1.0.2` 只到 TLS 1.2；要求 1.3 会让「用一台 CentOS 7 当客户端」直接连不上，
  而那正是我们已经验证过的那一档。
- **握手只验 CA，授权在 HTTP 层做**。也就是说：由本 CA 签发的客户端证书都能完成握手，
  而「这个身份被允许做什么」在 HTTP 层判、拒绝时给 **403 + `REMOTE_FORBIDDEN`**。
  理由不是偷懒，是**可诊断性**：如果在 `VerifyPeerCertificate` 里按 CN 拒掉，那么
  「证书没签对」与「身份没被授权」在客户端看来都是同一句 TLS 握手失败，运维分不清该改哪一边。
- 客户端侧（`opsctl`）用 `--ca-cert` 建 `RootCAs` 并按地址做标准的服务端校验（防中间人）。

### D3：身份 = 客户端证书的 **CN**；授权 = 「CN → scope + 可选应用白名单」，**默认拒绝**

```yaml
remote:
  clients:
    - cn: opsctl-central
      scope: write
      applications: [orders-api, billing-api]   # 省略 = 这台机上的全部应用
    - cn: opsctl-readonly
      scope: read
```

- **scope 只有两个取值**：`read`（只读端点）与 `write`（全部端点）。更细的角色是 5c 的事，
  5a 刻意只做最小的那一档——**能表达「只读」与「可写」的差别**，就已经把「把端口开出去」
  这件事的风险从「任何连上的人能做任何事」降到「名单里的人做名单里的事」。
- **不在名单里的 CN 一律拒绝**（白名单模型，不是黑名单）。
- `applications` 是**这台机器上的应用名**。省略表示全部。
- **授权粒度到端点，由路由表显式声明**：每条路由注册时必须给出 `accessRead` 或 `accessWrite`，
  **漏给编译不过**（不是默认值，是必填参数）。理由：一张「写端点清单」会随新端点漂移，
  漏登记一个就是静默放行；而把 scope 写在路由注册处，新端点不可能忘。

### D4：审计的 actor 以**认证身份**为准，`createdBy` 降级为「自报」

`remote` 形态下 `createdBy` 是**不可信输入**：任何能连上的人都能自称任何人。因此：

| 来路 | actor | 判据 |
| --- | --- | --- |
| Unix socket | 请求体里的 `createdBy` | 能连上 socket 就等于本地运维（socket 文件模式就是那道门），与今天行为**完全一致** |
| mTLS | **证书 CN**（`remote:<CN>` 形式，一眼能看出是远程来的） | 证书是唯一能自证的东西 |

自报值与认证值**不一致**时，审计的 `Details` 里额外记一条 `claimedBy`——「他自称是谁」也是
有用的线索，但它不许替代事实。

**实现落点**（这是这一片最要紧的正确性所在）：认证中间件把 `domain.Principal` 放进 `context`，
`application.Service.Create` 从 ctx 取 principal 决定 actor。**不**在每个 handler 里各自改写
`CreatedBy`——那样有八个写入口，漏一个就是一个能被冒充的审计条目。放 ctx + 应用层读，
新加的写端点自动获得正确行为。

`Principal` 只用于两件事：**「谁做的」与「远程能不能做」**，不参与业务决策（规格级别的纪律：
一旦它开始影响「怎么做」，上下文就成了隐藏参数）。

### D5：远程**禁止** `executor.command`

`executor.command` 是「在目标机上跑一条（在 `execution.allowedPaths` 白名单内的）程序」的
通用入口。它在本机 socket 形态下是合理的（等价于本地 shell），但把它暴露到网络上等于把
「有限制的任意命令执行」交给名单里的人。

**这是刻意的能力缺口，不是遗漏**：需要跑命令就在目标机上跑 `opsctl`，
或者用 `deploy` / `runtime.*` 这些有明确语义的操作。有独立断言钉住它。

### D6：`host.address` 从「标签」变成「连接参数」；**空仍表示本机**

- 兼容性：既有数据语义不变——本机记录本来就是空的。变化只发生在「填了地址的那些记录」上：
  它们以前只是给人看的字符串，现在会被真的拿去拨号。
- 形态**只接受 `host:port`**（`net.SplitHostPort` 能解析）。刻意不接受 `https://host:port`
  这类带 scheme 的写法：两种写法迟早会有一种在某处不被支持，而报出来的是「连不上」。
- 应用与主机的**归属**（「这个应用属于哪台主机」）不在 5a 里做，那是 5b（批量发布）的地基。

### D7：证书不进库、不进日志；**私钥文件模式过宽则 opsd 启动失败**

- 私钥与证书**只走文件路径**，明文绝不进 DB / 日志 / 审计——与 `SecretRef` 的纪律同一条。
  `/identity` 只回 CN，不回任何密钥材料或指纹以外的内容。
- **私钥文件模式必须 ≤ `0600`，属主必须是 opsd 的运行用户**，否则 `opsd` **拒绝启动**。
  不是警告：一份 `0644` 的私钥等于把机器身份公开了，而它不会自己变回去。
  （秘密文件那条路已经有一个同样的检查，见 `TestSecretFileWithLoosePermissionsIsRejected`。）
- `opsctl` 侧的客户端私钥同样要求 ≤ `0600`。

### D8：`opsctl` 的目标选择：`--host <name>` 与 `--remote <addr>`，都与 `--socket` 互斥

- `--host <name>`：从**本机库**里查那条记录的 `address`，再连过去。
- `--remote <addr>`：直接给地址，**不查库**。存在的理由很具体：**排障时本机 `opsd` 可能正好
  没起来**，而那时最需要的就是「我还能连上那台机吗」。
- 两者同时给、或与 `--socket` 同时给 → `INVALID_REQUEST`（退出码 2）。

### D9：只读汇总在 5a 只做「主机可达性」，且**不落库**

`opsctl host list --check`：先连本机读主机列表，再依次连每一台登记的远程主机，逐行报
「可达 / 不可达 + 原因」，最后一行汇总（N 台可达 / M 台不可达）。

**探测结果不写库**：写进去就会出现「库里说可达、其实三小时前就挂了」——迭代 4c 刚为
「第二份会过期的真相」做过一整套对账，不在这里再造一个。

跨主机的**应用清单汇总**需要「应用属于哪台主机」，那是 5b 的事。

### D10：证书的签发与轮换**不做**

运维用 `openssl` 生成 CA 与每台机的证书，本文给出确切命令（含 SAN）。工具**只消费**证书。
「自动签发 / 自动轮换」记为**未实现**——不得写成「已支持」（见第 11 节）。

### D11：三个新错误码，各自指向不同的修法

| 错误码 | HTTP | 退出码 | 含义 | 去修什么 |
| --- | --- | --- | --- | --- |
| `HOST_UNREACHABLE` | 502 | 33 | 连不上目标主机的 `opsd`（连接被拒、超时、DNS 失败） | 网络、对端有没有在跑、端口对不对 |
| `HOST_TLS_FAILED` | 502 | 34 | 连上了但 TLS 没通过（证书不受信、过期、SAN 不匹配、本机没有客户端证书） | 证书 |
| `REMOTE_FORBIDDEN` | 403 | 35 | 身份认出来了，但这次操作不在它的授权范围内 | 配置里的 `clients` 名单 |

三者刻意分开：**放在一起报「连不上」会让三种完全不同的修法混成一句**。

### D12：新增 `GET /api/v1/identity`

`health` 回答「你活着吗」，`identity` 回答「你是谁、我以什么身份连上来的、这次走的是哪条路」：

```json
{ "apiVersion": "ops.frz.io/v1alpha1",
  "hostname": "vm-43-142",
  "daemonVersion": "…",          // 构建版本；未注入时为空串
  "startedAt": "…",
  "applications": 3,             // 这台机上有几个应用
  "backend": "tls",              // unix | tls —— 这次请求走的是哪条路
  "clientCn": "opsctl-central",  // 认证结果；socket 形态下为空
  "scope": "write",              // read | write；socket 形态下是 write
  "applicationsAllowed": ["orders-api"] }
```

`backend` 与 `clientCn` 是这张响应里最有用的两个字段：**「我明明给了 `--host`，怎么打到了本机」
必须一眼看得出来**，而「我以什么身份连上来的」是排授权问题的第一句话。

## 4. 配置增量（`opsd`）

```yaml
# 不配这一段 = 不听 TCP，形态与今天完全一致。
remote:
  listen: "0.0.0.0:9443"
  certFile: /etc/opsd/pki/server.crt
  keyFile: /etc/opsd/pki/server.key
  clientCAFile: /etc/opsd/pki/ca.crt
  clients:
    - cn: opsctl-central
      scope: write
      applications: [orders-api, billing-api]
```

校验（全部返回 `CONFIG_INVALID`，即启动失败）：

- `listen` 非空时，`certFile` / `keyFile` / `clientCAFile` **都必填**；
- `listen` 为空时，这一段的其他字段**都不许给**（配了但不听是最容易误读的状态：
  运维以为开了远程，其实没有）；
- 私钥文件模式 ≤ `0600` 且属主为运行用户（D7）；
- `clients` 非空、`cn` 非空且唯一、`scope` ∈ {`read`, `write`}、`applications` 里的名字非空。

## 6. CLI 增量

| 命令 | 说明 |
| --- | --- |
| `opsctl --host <name> <命令>` | 打到那台机上的 `opsd`（地址从本机库读） |
| `opsctl --remote <addr> <命令>` | 直接打到那个地址（不查库；排障用） |
| `opsctl --client-cert/--client-key/--ca-cert` | 客户端身份与信任根；也可用环境变量 |
| `opsctl host check <name>` | 连过去问身份：对方主机名、地址、`daemonVersion`、`backend`、我方 CN 与 scope、对端应用数 |
| `opsctl host list --check` | 逐台探活并汇总（D9） |

- `host create --address <host:port>` 今天的 `--address` 已经是这个语义，只补校验与文档。
- 私钥模式检查在 `opsctl` 侧同样执行（D7）。

## 7. 数据表：**不动**

5a 不改任何表，也不加表。理由写成规矩：`host` 记录只承载「它叫什么、在哪」，
**可达性不落库**（D9）、**证书不落库**（D7）。多主机的状态由用户 2026-09-27 拍板为
「各机自己的库 + 中央只读汇总」（第 10 节），因此也不建中央库。

## 8. 兼容性与迁移影响

- **默认行为逐字节不变**：没有 `remote` 段就不听 TCP；`--host` / `--remote` 不给就走 socket。
  1c 起的所有断言与 `make verify-linux` 的全部既有项都必须原样通过（有回归断言）。
- **`host.address` 的语义**：从「标签」变成「连接参数」，但**空 = 本机**不变，
  既有数据不需要迁移。改动只有一处：填了地址的记录会被真的拨号（D6）。
- **审计的 actor**：`remote` 请求的 actor 从「自报」变成「认证身份」——这是**行为变化**，
  而且是这一片要解决的问题本身。本地 socket 请求的 actor 语义不变（D4）。
- **错误码**：新增三个（D11），已登记进 `api/v1` 的映射表与本文档。
- **新增配置段 `remote`**：同一 `apiVersion` 内新增**可选**段，兼容；不带它的配置行为不变。
- **`make verify-linux` 的断言数**：5a 会加（e2e 与容器各一部分），以脚本运行时打印的数字为准。

## 9. 验收标准（5a）

每一条都给「命令 / 结果 / 证据类型」。

1. **默认不听 TCP**：不配 `remote` 的 `opsd`，对它的端口做一次连接尝试**失败**；
   `/identity` 走 socket 返回 `backend: unix`。【集成测试】
2. **mTLS 双向校验真的生效**：无客户端证书、或用**另一个 CA** 签的客户端证书，握手失败，
   `opsctl` 报 `HOST_TLS_FAILED` 且信息里说清是哪一种（本机没有证书 / 对端证书不受信 /
   证书过期）。【集成测试 / e2e】
3. **服务端身份被校验**：客户端拿一份**不被信任**的服务端证书时拒绝连接（防中间人），
   报 `HOST_TLS_FAILED`。【e2e】
4. **授权默认拒绝**：CN 不在名单里 → `REMOTE_FORBIDDEN`（403），且**拒绝发生在动手之前**
   （不许先建 Operation 再失败）。【e2e】
5. **scope 生效**：`read` 身份对写端点 → `REMOTE_FORBIDDEN`；对读端点 → 正常。【e2e】
6. **应用白名单生效**：`write` 身份操作名单**外**的应用 → `REMOTE_FORBIDDEN`；
   名单内的应用 → 正常。【e2e】
7. **远程的写操作落在目标机的库上**：经远程提交一次部署，**目标机**的库里查得到这条
   Operation，**发起方**本机的库里没有。【e2e】
8. **审计记的是认证身份**：远程提交时 `createdBy` 自报一个假名字，审计的 actor 是证书 CN，
   且 `Details` 里能看到 `claimedBy`。【集成测试 / e2e】
9. **远程禁止 `executor.command`**：被拒，且错误码说明这是刻意的限制。【e2e】
10. **私钥模式过宽则拒绝启动**：把服务端私钥改成 `0644`，`opsd` 起不来并指出是这个文件；
    `opsctl` 侧的客户端私钥同样。【Linux 容器】（文件模式是真机/容器语义）
11. **`host check` 报出对方身份与我方身份**：`backend: tls`、`clientCn` 是我方证书的 CN、
    `scope` 与配置一致。【e2e】
12. **`host list --check` 汇总**：一台可达 + 一台不可达 → 逐行给出原因，最后一行汇总；
    **库里的记录一字未改**（不落库）。【e2e】
13. **回归**：`make ci` 与 `make verify-linux` 全绿，既有断言一条不少。【静态 / 单元 /
    集成 / e2e / Linux 容器】

## 10. 已冻结的决定（用户 2026-09-27 拍板）

1. **远程形态 = 每台机装 `opsd`（agent）**，不做 SSH 执行器。理由见 D1。
2. **5a = 远程连接与主机注册**（先把「能连上另一台机上真的 `opsd`」打通，
   语义与本地完全一致），可观测性/通知、RBAC/审批、备份灾备分别留给 5c/5d/5e。
3. **多主机的状态 = 各机自己的库 + 中央只读汇总**，不建中央库。理由：不引入单点，
   也不重新制造「库说 A、机器上实际是 B」的双真相问题（4c 刚为它做过对账）。
4. **认证 = mTLS 双向证书，每机一对**；不引第三方依赖（标准库 `crypto/tls`）。
   授权在 5a 只到 scope + 应用白名单，更细的 RBAC 留在 5c。

## 11. 未验证内容（规格阶段就写明）

- **证书的签发与轮换不做**（D10）：没有「一条命令把新机器接进集群」的能力，
  也没有过期前的自动轮换或吊销（CRL/OCSP 都不做）。运维拿 `openssl` 手工来。
- **跨物理主机**：5a 的证据是「同一台机上两个 `opsd` 实例互连」与容器/e2e。

- **批量发布、跨主机汇总应用清单**：5b，本片不做（需要「应用属于哪台主机」）。

## 12. 实现记录（5a）

### 12.1 新增与改动

**新包 `internal/pki`**：把证书与私钥文件变成 `crypto/tls` 配置，并在读之前检查私钥
文件的模式与属主。它被 opsd（服务端）与 opsctl（客户端）共用——两边对「什么样的私钥
才算合格」的判据只有一份，一边松一边紧是最容易出的事，而松的那边不会报警。

**配置 `remote` 段**（`internal/adapters/config/remote.go`）：结构 + 全部校验。
校验失败一律 `CONFIG_INVALID`（启动失败），不是警告。

**HTTP 层的两件事**（`internal/adapters/httpapi/authz.go`）：

- `Server.routes()` 成了**唯一**的路由注册处：路径、访问档位与处理器写在同一行。
  档位不是默认值而是必填，漏写就是启动即崩（`Handler()` 里检查并 panic）。
  理由写在代码里：一张单独的「写端点清单」会随新端点漂移，漏登记一个就是**静默放行**。
- `authenticate` 中间件做认证与授权，**必须在 mux 之后**：路由的档位是从匹配到的
  pattern 查的，而在 `mux.Handler(r)` 之前根本不知道这次请求落到哪条路由上。
  用 mux 自己解析出的 pattern 而不是自己再写一遍路径匹配——两套匹配迟早漂移，
  而漂移的那一天报出来的是「明明配了权限却放行了」。

**领域身份**（`internal/domain/principal.go`）：`Principal`（Kind/Name/Scope/
Applications）、`RemoteIdentity`、`WithPrincipal`/`PrincipalFrom`、`ClaimedActor`、
`RemoteForbidden`。只用于两件事：**谁做的**与**远程能不能做**。

**`application.Service.Create`** 的三处：远程禁 `executor.command`、应用白名单
（判在**解析之前**：先回答「归不归你做」，再回答「现在做不做得了」）、决定 actor。

**审计**：`operation.created` 的 actor 取 `op.CreatedBy`（应用层已按来路定好）；
自报值与认证值不同时把自报值写进 `details.claimedBy`。`domain.Operation` 上的
`ClaimedBy` 字段**刻意不落库**——让同一件事在库里存两份、其中一份不可信，
是后面每次查询都要小心避开的坑。

**API**：新增 `GET /api/v1/identity`；新增三个错误码 `HOST_UNREACHABLE`(502/33)、
`HOST_TLS_FAILED`(502/34)、`REMOTE_FORBIDDEN`(403/35)。

**CLI**：`--host` / `--remote` / `--client-cert` / `--client-key` / `--ca-cert`
（后三个有 `OPSD_CLIENT_CERT` / `OPSD_CLIENT_KEY` / `OPSD_CA_CERT` 环境变量兜底）；
目标解析放在 `PersistentPreRunE` 里，互斥检查只有一处。新增 `opsctl identity`
（规格的 CLI 表里只写了 `host check`，但「我打到了哪台机、以什么身份」值得有一条
直接问的命令，而 `host check <name>` 要求先有一条主机记录）、`opsctl host check
<name>`、`opsctl host list --check`。

**远程监听**：`httpapi.ListenTLS` 起 `tls.Listener`，交给同一个 `Server.Serve`
（`http.Server.Serve` 会在 `*tls.Conn` 上握手并填好 `r.TLS`，而 `r.TLS` 正是中间件
区分两条路的唯一判据）。远程监听挂了不让本机跟着停：它是这个守护进程的一个可选能力，
失败记 Error 级日志，不静默降级。

### 12.2 访问档位表

只读（`accessRead`）：全部 `GET`、`POST /artifacts/{id}/verify`（只重算摘要比对，
不改状态）、`POST /applications/{id}/runtime/validate`（同步、无副作用）。
其余 `POST`/`PUT`/`DELETE` 都是 `accessWrite`。`POST /artifacts/gc`、`POST
/backups/prune` 这两条「同步但会删东西」的端点是写——它们不改数据库之外的状态，
但删掉的是真实内容。

### 12.3 实现中发现并修掉的两个真问题

1. **应用白名单一次都没生效过**。中间件里用 `r.PathValue("id")` 取应用引用——但路径
   参数是 `ServeMux` 在**派发时**填进去的，而中间件跑在它之前，取到的永远是空串，
   于是直接放行。这个 bug 只在「把名单外的应用应当被拒写成断言」时才暴露；读代码
   看过去，那句 `if ref == "" { return nil }` 像一个正常的边界处理。
2. **`mux.Handler(r)` 返回的 pattern 带方法**（`GET /api/v1/applications/{id}`）。
   第一版前缀判断因此永远不成立——与上一条叠加，白名单有**两道**都会静默放行。
   现在先剥掉方法前缀再比。

两条都记在这里，是因为它们属于同一类：**授权代码失效时不报错**。这也是为什么这一片
把「名单外的应用应当被拒」写成了断言而没只依赖代码审查。

### 12.4 授权粒度上刻意的边界（写清楚，免得被读成漏了）

- **应用白名单只管应用**。备份类的资源是策略名与备份 ID，与「哪台机上的哪个应用」
  无关，因此不受应用白名单约束——它们由档位（read/write）管。更细的留给 5c 的 RBAC。
- **`executor.command` 对远程全禁**（规格 D5），不是「按白名单放行」：一个能跑任意
  argv 的入口，开一条缝就等于全开。
- **应用白名单只覆盖「针对某个应用」的端点与操作的创建**。`GET /operations/{id}`、
  `/artifacts/*`、`/backups/*`、`/hosts/*`、`/schedules/*` 这些**与具体应用无关**的端点
  只受档位（read/write）约束——带应用白名单的 write 身份可以读这台机上任何一条操作记录。
  这不是遗漏，是 5a 授权粒度的边界；要按资源细分得等 5c 的 RBAC。
- **`--host` / `host check` / `host list --check` 拨号用的证书要显式给**（三个旗标或
  环境变量）。`--host` 只解决「地址从哪儿来」；证书仍然在运维手上（D7：工具只消费
  证书）。这条写进了旗标说明，也在 e2e 里钉住。

### 12.5 顺带修掉的一个既有缺口

配置校验失败时，全部问题原本只放在 `Details["problems"]` 里，而 `Details` 目前
**没有任何一处会被打印**——运维看到的只有一句「config is invalid」。现在这些问题
同时逐条列进 message。这不是 5a 的需求，但 5a 的验收标准（「私钥模式过宽要指出是
哪个文件」）依赖它，而且它让所有既有配置错误的可用性一起变好了。

### 13.2 e2e（真进程、真 TLS，平台无关）

证书在测试里用 `crypto/x509` 现签（签进仓库的 PEM 会过期，而一个「过两年自己坏掉」
的测试比没有测试更糟）。用例：

- **默认不听 TCP**：同一个端口，有 `remote` 段时连得上；去掉 `remote` 段之后连不上
  （`HOST_UNREACHABLE`，退出码 33），而 socket 那条路照旧。
- **身份报得对**：`backend` / `clientCn` / `scope` / 应用白名单 / hostname，
  以及人类可读输出里带上地址。
- **没带客户端证书** → `HOST_TLS_FAILED`(34)，且报错说清是缺客户端证书。
- **另一个 CA 签的客户端证书**（CN 一模一样）→ `HOST_TLS_FAILED`(34)。
- **本 CA 签的、CN 不在名单里** → `REMOTE_FORBIDDEN`(35)，报错回显那个 CN。
- **客户端校验服务端**：拿不信任的 CA 去连 → `HOST_TLS_FAILED`(34)。
- **只读档位**：读端点通、写端点 `REMOTE_FORBIDDEN`(35)。
- **远程写操作落在目标机的库上**：经远程跑一次备份，目标机库里有这条 `backup.run`、
  发起方库里没有；且审计的 actor 是 `remote:opsctl-central`、`details` 里有
  `claimedBy: alice`（请求体里自报的假名字）。
- **远程禁 `executor.command`**：退出码 35，且目标机库里一条都没留下。
- **`host check` 与 `host list --check`**：一台可达 + 一台不可达 → 逐行给出原因、
  汇总行 `2 台可达，1 台不可达（共 3 台）`（本机那条记录也算一台，按 socket 探），
  跑完之后主机记录**一字未改**。
- **三个目标旗标互斥**（`--socket` / `--host` / `--remote`），`--host` 指向本机记录
  时也给出明确说法。
- **私钥 0644 时 opsd 拒绝启动**，报错指出是哪个文件、该怎么办、错误码是
  `CONFIG_INVALID`。

### 13.3 证据类型的更正（规格 §9 第 10 条的说明）

规格里把「私钥模式过宽则拒绝启动」写成了【Linux 容器】。实际落在 **e2e**：这条检查
是一次 `os.Stat` 加一次 uid 比对，没有 Linux 特有的语义，而 e2e 能在两个平台与 CI 上
都跑。容器 harness 里不再重复加一遍——**重复的断言不会提高证据强度，只会提高维护成本**。
如果将来那条检查引入了属组、ACL 或 SELinux 相关的内容，再把它移进容器。

### 13.4 回归（Linux 容器）

`make verify-linux` —— **232 项通过 / 0 项失败**，**证据类型是「Linux 容器」**
（Ubuntu 24.04 / systemd 255 / 真 Nginx / 真 curl，本机 arm64 上的 OrbStack）。
断言数与 4c 落地时**完全一致**：5a 一行容器断言都没加，因为这一片没有引入新的
内核级语义（那条「私钥模式过宽」在 e2e 里验，见 13.3 的说明）。这一条跑的是
**回归**——路由表被重写过（改成单一来源的 `routes()`）、配置校验多了一段、
HTTP 处理器外面多了一层中间件，三者都可能把既有行为弄坏，而 232 项全部原样通过
说明没有。

日志里能看到 5a 的默认形态确实生效：`remote listener is disabled` + `reason:
remote.listen is not configured`——容器里的 opsd 配置不带 `remote` 段，
于是完全不听 TCP，形态与 4c 一致。

  `test/host/verify.sh` 这一轮没有加远程段（那台机上只有一个 opsd 实例，
  加一段「自己连自己」的远程验证，证据强度不高于已在本机与 CI 上跑过的那两轮）。
- **证书的签发与轮换**：不做（D10）。没有「一条命令把新机器接进集群」，也没有
  过期前的轮换或吊销（CRL/OCSP 都没有）。运维拿 `openssl` 手工来。
- **SELinux 与防火墙对监听端口的影响**：本工具不安装策略模块、也不改防火墙规则。

- **批量发布、跨主机应用清单汇总**：5b（需要「应用属于哪台主机」）。
