## 1. 定位与前置

迭代 3 把前两个迭代的底座接成**一条真正的发布链路**：上传的制品 → 解包成一个带版本的
release 目录 → 起进程 → 健康通过才算发布成功 → 失败就回到上一个稳定版本。

1c 已经把「进程」这一层做完了（unit 渲染、启停、就绪探测、凭据投递）。迭代 3 补的是
**制品与版本**这一层：今天 manifest 里的 `artifact.id` 只是一条声明，真正被执行的
`exec.argv[0]` 是运维手工放上去的路径（容器 harness 里就是这么做的）。**这个缺口正是
本迭代的核心**：让「声明的东西」真的成为「运行的东西」。

## 2. 范围与里程碑拆分

迭代 3 的量级与迭代 2 相当，因此同样拆成能**独立验证**的三片：

| 里程碑 | 内容 | 为什么能独立验证 |
| --- | --- | --- |
| **3a** | `ReleaseAdapter` 端口与解包实现（`none` / `tar` / `tar-gz` / `zip` + `stripComponents`，含路径穿越防护）；manifest 增量字段（`artifact.version`、`resources`、`release`）与严格校验；argv 的解析规则 | 解包是纯文件系统操作，临时目录里就能跑完整断言，且**不需要 systemd** |

### 本迭代整体不做

- **蓝绿、two-slot 并行、Nginx upstream 与切流**（迭代 4）。因此**本迭代不定义** Nginx 相关
  字段——理由见 D9。
- **增量/差量发布**、灰度（按比例放量）、按主机分批：路线图第 6 节没有要求，且在没有真实
  需求前把它做进模型等于把层次猜错。
- **构建**（从源码编译）：制品仍是外部产出、上传后不可变。opsd 不做 CI 的活。
- **回滚到"更早的任意版本"之外的策略**（如按健康指标自动回滚到 N 个版本之前）。

## 3. 关键决策

### D1：解包是**独立端口**，不是 `RuntimeAdapter` 的方法

解包（归档格式、`stripComponents`、路径穿越防护）与「进程管理」是正交的两件事：

- `RuntimeAdapter` 的两个实现（systemd / proc）都要用它，**放进去就得各写一遍**——注释里
  写着的「不允许各自实现一份」在这里同样适用；
- 应用层不做 IO（`internal/domain` 纯逻辑、`internal/application` 只编排），因此它不可能
  是应用层的私有函数；
- 与 `BackupAdapter` 同构：**端口在 `internal/application`，实现在 `internal/adapters`**。

```go
// ReleaseAdapter 把一份制品物化成一个可运行的 release 目录，并管理版本的切换与清理。
type ReleaseAdapter interface {
	// Materialize 把制品字节解到该 release 的目录里。目录由实现创建（模式与属主按 1c 的约定：
	// 0750、runUser:runUser）。**已存在的目录必须被拒绝**——制品不可变，复用一个目录等于
	// 允许"同一个版本号下换了内容"，那是最难查的一类漂移。
	Materialize(ctx context.Context, spec *domain.ApplicationSpec, releaseID string, artifact io.Reader) error
	// Activate 把 current 指针切到该 release（见 D3）。必须是原子的：运维可能在任意时刻重启。
	Activate(ctx context.Context, spec *domain.ApplicationSpec, releaseID string) error
	// Remove 删掉一个 release 目录。实现必须**拒绝删除 current 指向的那个**。
	Remove(ctx context.Context, spec *domain.ApplicationSpec, releaseID string) error
	// List 列出磁盘上实际存在的 release 目录（用于发现"库里有记录、盘上没目录"这类不一致）。
	List(ctx context.Context, spec *domain.ApplicationSpec) ([]string, error)
}
```

**不建共享合约测试**（与 `runtimecontract` / `backupcontract` 不同）：合约测试的价值在于
钉住**多个实现之间**的一致性，而这里只有一个真实实现，且它的行为（解出来的文件、模式、
路径）完全可以用真实文件系统断言。为单个实现造一套合约是仪式，不是保障。将来若出现第二个
实现（如解包到只读挂载），再把它的断言提炼成合约。

### D2：版本身份 = `Release` 记录；`artifact.version` 是它的来源

- `Release.ID`（`rel_…`）是**身份**，release 目录名用它；
- `Release.Version` 是**人类可读的版本号**，来自 manifest 新增的 `artifact.version`；
- 两者分开：ID 不可变且唯一，Version 用于展示、回滚引用与保留策略的排序依据。

**版本号不可复用**：`releases` 表已有 `UNIQUE (application_id, version)`。规则定为：
同一应用下重复提交同一个 version，若**制品相同**（`artifact_id` 与 digest 都一致）则**幂等**
返回既有记录；**制品不同则 `RELEASE_CONFLICT`**——同一个版本号下换内容是最难查的一类漂移。

### D3：切换机制是 `current` 符号链接

`<releases 根>/current` 是一个符号链接，指向当前激活的 release 目录；**unit 只写一次**，
它的 `ExecStart` 与 `WorkingDirectory` 解析后落在 `current` 之下。

理由（**这条是待确认的两条之一**，见第 11 节）：

- 与 `unitfile` 里既有的注释一致：「把整个 releases 根纳入可写路径，后续无论解包到哪个
  releaseID 都在授权范围内，**不必每发一个版本就重写 unit**」；proc 适配器也已经引用了
  `releases/current`；
- 切换是**一次原子 rename**（建 `current.tmp` 再 `rename` 覆盖），不需要 `daemon-reload`，
  运维在切换的任意瞬间重启 systemd 都不会读到半成品；
- 「现在跑的是哪个版本」= 解析 `current` 指向 → 与磁盘上的事实天然一致，不会出现
  「unit 说是 A，目录被换成 B」的第二处真相。

代价（必须写清楚）：unit 文件里看不出具体版本，排查时要用 `list` 或读链接；保留策略
**绝不能删 current 指向的目录**（D7 里有对应断言）。

另一种做法是**每个 release 一个 unit 文件**（unit 里写明具体 release 目录）：好处是
`systemctl cat` 直接可读，代价是每次部署都要重写 unit + `daemon-reload`，且「跑的是哪个
版本」变成两处记录，回滚要重写 unit。

### D4：argv 的解析规则：**只解析 `argv[0]`，其余一个字节都不动**

| 位置 | 形态 | 解析 |
| --- | --- | --- |
| `argv[0]` | 绝对路径（`/usr/bin/java`、`/opt/jdk-17.0.1/bin/java`） | 原样使用 |
| `argv[0]` | 相对路径（`bin/server`） | `<releases 根>/current/<相对路径>` |
| `argv[1:]` | 任何形态 | **原样**（由进程按自己的 `workingDirectory` 解释） |

> **2026-09-24 实现时修正**：D4 原本写的是「每个元素都按这条规则解析」。写测试时发现那是
> **错的**：除了 `argv[0]`，没有任何办法判断一个参数**是不是路径**。`-Xmx512m`、
> `-Dlogging.file=/var/log/app.log` 看起来都像相对路径（后者还含斜杠），一旦被拼成
> `<current>/-Xmx512m`，进程收到的是一个被**静默改写**的参数——不是报错，是行为变了，
> 而这是最难查的一类失败。`argv[0]` 则非解析不可：systemd 要求它是绝对路径（219 那一档
> 尤其如此），而「相对路径」正是「制品里的那个可执行文件」的表达。

这样 go 与 java 用**同一条规则**，不需要为 Java 发明第二套拼装逻辑：

- Go：`argv: [bin/server, --config, /etc/myapp/config.yaml]`——`argv[0]` 解析到 release 里，
  `--config` 之后是进程自己的事；
- Java：`argv: [/opt/jdk-17.0.1/bin/java, -Xmx512m, -jar, app.jar, --port, 8080]`——
  **java 路径与 JVM 参数都是显式写在 argv 里的**；`app.jar` 由 java 按
  `exec.workingDirectory` 解释，因此 Java 的 `workingDirectory` 应当写成 release 的
  `current`（约定路径，稳定）；`runtime: java` 只决定校验（`argv[0]` 必须是绝对解释器路径）。

路线图要求「Java 允许显式配置 Java 路径和 JVM 参数」，写进 argv 满足这一点，且**不引入
第二处 argv 拼装**：拼装逻辑（`[java.path, ...java.args, ...exec.argv]`）是将来最容易漂移
的地方——单位从「毫秒」变成「秒」这种改动只要漏一处就会静默出错。

**安全边界**：相对 `argv[0]` **不得包含 `..`**（在 manifest 校验期就拒），且拼接结果必须仍在
`<releases 根>/current/` 之下（解析时做一次前缀校验）。这是路径穿越的第二道防线
（第一道在解包时，见 D5）——manifest 作者能写 argv，而 argv 会变成 `ExecStart=`。

### D5：解包必须防「tar slip / zip slip」

解包是**唯一**会把外部字节变成可执行文件的地方，因此三条一起做：

1. **条目名逐条校验**：不得是绝对路径、不得含 `..`（与 `files` 备份适配器的
   `validateEntryName` 同源，规则一致）；
2. **两趟写入**：先目录与普通文件，**符号链接与硬链接留到第二趟**。这样「先用一个链接把
   后续条目引到目录之外」这条路走不通——第一趟里根本没有链接；
3. **链接本身也要校验**：符号链接的目标允许指向 release 之外（共享库、`/etc` 下的配置是
   正常用法），但**硬链接的目标必须在 release 之内**（硬链接是"同一个 inode 的第二个名字"，
   指向外面等于把宿主文件变成 release 的一部分）。

`stripComponents` 按 GNU tar 的语义：先剥掉前 N 层再校验条目名；剥完之后为空的条目跳过。

### D6：部署是一个 Operation；**健康通过才算发布成功**

`app.deploy` 走 `Service.Create`（复用锁、幂等键、请求摘要、审计、日志、取消）——
与 `runtime.*`、`backup.*` 完全同一条路，没有第二条旁路。序列：

1. 解析 version / artifact / unpack（**创建期**就完成，能在排队之前报的错不留给 worker）；
2. 物化：打开制品 → **校验 digest**（manifest 声明了 `artifact.digest` 就必须匹配）→
   解包到新 release 目录；
3. 准备：写 unit（若需要）+ 写环境文件与凭据（复用 1c 的 `Prepare`）；
4. 切换：`Activate` 到新 release；
5. 启动，然后**由部署流程轮询就绪**直到通过或超过 `health.startTimeoutSeconds`；
6. 成功 → 记 `Release` 为 active、执行保留策略、写审计。

> **2026-09-24 实现时修正**：D6 原本写的是「启动 + 就绪检查（复用 1c 的 runtime.start
> 语义）」。写代码时发现 1c 的 `runtime.start` **不等待就绪**——「启动 ≠ 就绪」是它刻意保留
> 的区分（进程活着不等于能接流量），就绪要通过单独的 `health` 去问，超时预算由适配器在
> 超过 `startTimeout` 之后以 `RUNTIME_NOT_READY` 表达。因此「健康通过才算发布成功」这件事
> **必须由部署流程自己做**：`Start` 之后轮询 `Health`（间隔 200ms），直到 `Ready` 或超过
> `spec.Health.StartTimeout`。连续成功次数的计数仍在适配器里（`Health` 只在达成后报 Ready）。

**失败时**（第 2–5 步任一步）：

- 若**已经切换**（第 4 步之后失败）：把 `current` 切回原目标并重启 → **保留当前稳定版本**，
  这就是路线图流程 6 的「失败时只清理未激活 release，保留当前稳定版本」；
- 删除**本次新建**的 release 目录（它从未被激活过）；
- 若原本**没有** current（首次部署）：停掉 unit、删掉新目录；
- Operation 以 `DEPLOY_ROLLED_BACK`（D10）失败，消息里写明现在跑的是哪个版本。

### D7：保留策略：`release.keepLast`，**永不删 current**

- 默认 `keepLast: 5`（够回滚好几个版本，又不至于把盘占满；`0` 表示不自动清理）；
- 在**部署成功后**执行，只在同一应用的 release 目录之间；
- **永不删 current 指向的那个**（保底：即使 `keepLast=1` 也留着它）；
- 删除顺序：先库里的记录后目录？——**反过来**：先用 `ReleaseAdapter.Remove` 删目录，
  再标记记录为 `removed`。理由是「库里说在、盘上没了」比「盘上有、库里没有」更容易让人
  误判：前者会让人以为某个版本还能回滚（回滚失败），后者只是占一点盘。
  **这条与备份的 D9（先标记后删）方向相反，必须写清楚为什么**：备份那边丢的是**内容**，
  而这里丢的只是**可执行文件的一份副本**（制品永远在制品库里，重新解包即可恢复）。

### D8：`application_specs` 按 release 版本化（1c 决定 3 的落地）

- 迁移 `0009`：把 `application_specs` 从「应用一行」改成「应用 + release 一行」。
  SQLite 改不了主键，因此用标准的重建流程（建新表 → `INSERT … SELECT` → 删旧表 → 改名），
  既有行迁移为 `release_id = NULL`（表示"应用级当前规格"，语义与今天一致）；
- **部署时**把该 release 的 spec 写进 `(application_id, release_id)` 行；
- **回滚时**读回目标 release 的 spec，**连配置一起回滚**——这正是 1c 决定 3 的理由；
- 老行（`release_id IS NULL`）继续被 `spec get` 读到，行为不变。

### D9：本迭代**不定义** Nginx / slot 相关字段

路线图第 6 节的 manifest 清单里有「Nginx upstream 名称、域名/监听入口和发布策略」，但
1c 的第 14 节已经把「slot 与蓝绿、Nginx、切流与回滚」明确划给**迭代 4**。

**本迭代一个字段都不加**，理由是 2d 里已经踩过的那条：**声明一个没人实现的东西，无论
接受还是拒绝都比不声明更糟**——接受就是静默忽略（运维以为切流配好了），拒绝就是让人写不了
manifest。字段属于**实现它的那个迭代**。迭代 4 加这些字段时按同一 `apiVersion` 内新增可选
字段处理（兼容），除非它改变了必填性。

### D10：错误码增量

| 错误码 | HTTP | 退出码 | 用途 |
| --- | --- | --- | --- |
| `DEPLOY_ROLLED_BACK` | 409 | 29 | 部署失败，**已回滚**到上一个稳定版本（进程与配置都回到原状态） |
| `ARTIFACT_UNPACK_FAILED` | 409 | 30 | **制品解不开**：不是 tar/zip、条目名逃出 release 目录、落点已被符号链接占住……（3a 实现时补：它与 `MANIFEST_INVALID` 刻意分开——manifest 没问题，运维要做的事是重新上传制品，不是改 manifest） |

**为什么值得单开一个码**：运维在部署失败后要问的第一个问题是「现在线上跑的是哪个版本」。
用 `RUNTIME_NOT_READY` 之类表达会把「已经回滚了」这件事埋进消息文本里，而它恰好决定了
要不要立刻人工介入。**不加入 1d 的重试白名单**：部署失败通常不是瞬时故障，自动重试会
把同一个坏版本反复推上去。

其余复用既有码：制品摘要不符用 `ARTIFACT_CHECKSUM_MISMATCH`、版本号冲突用
`RELEASE_CONFLICT`、release 不存在用 `RELEASE_NOT_FOUND`、就绪失败本身仍是
`RUNTIME_NOT_READY`（作为 `DEPLOY_ROLLED_BACK` 的 details 带出来）。

## 4. 模型冻结（manifest 增量）

现有字段（`runtime` / `artifact` / `exec` / `health` / `logs` / `systemd`）**一个都不改
语义**，只新增以下字段。同一 `apiVersion`（`ops.frz.io/v1alpha1`）内新增**可选**字段是
兼容的（1c 已定的规则）。

```yaml
apiVersion: ops.frz.io/v1alpha1
kind: ApplicationSpec

application: orders-api
runtime: go                     # go | java

artifact:
  id: art_xxx
  digest: sha256:...            # 新增（可选）：声明了就必须与实际一致
  version: 1.2.3                # 新增（可选，缺省按 digest 派生）：Release.Version 的来源
  fileName: bin/server          # 新增（可选，仅 strategy=none）：制品字节在 release 里的落点
  unpack:
    strategy: tar-gz            # none | tar | tar-gz | zip
    stripComponents: 1

exec:
  argv:
    - bin/server                # 相对路径 → <releases>/current/bin/server
    - --config
    - /etc/orders/config.yaml   # 绝对路径原样
  workingDirectory: /var/lib/orders-api
  runUser: orders-api
  ports: [8080]

resources:                      # 新增（可选）
  cpuQuotaPercent: 200          # → CPUQuota=200%
  memoryMaxBytes: 536870912     # → MemoryMax=512M

release:                        # 新增（可选）
  keepLast: 5                   # 保留最近 N 个 release 目录（0 = 不自动清理）
```

校验要求（新增部分，全部返回 `MANIFEST_INVALID`）：

- `artifact.version`：非空，字符集与 `application` 同源（它会进日志、审计与回滚引用），
  **不得含 `/`**（它是版本标签，不是路径）；
- `artifact.digest`：给了就必须是合法的 `sha256:<64 位小写十六进制>`；
- `resources.cpuQuotaPercent`：`0`–`10000`（`0` = 不限制）；`memoryMaxBytes`：`0` 或
  ≥ `16 MiB`（再小的值只会让进程一起就 OOM，那是配置错误而不是意图）；
- `release.keepLast`：`0`–`100`；
- `exec.argv[0]` 的相对形态**不得含 `..`**（见 D4 的安全边界）。

> **2026-09-24 实现时删掉的一条**：原本这里写着「`runtime: java` 时 `argv[0]` 必须是绝对路径，
> `runtime: go` 时必须是相对路径」。**没有采用**：1c 起就允许绝对 `argv[0]`（容器 harness 的
> 夹具就是这么写的），把它收紧成非法属于**改变必填性/形态**的破坏性变更，要提升
> `apiVersion`——为一条风格约束付这个代价不值。「编译产物住在 release 里」作为**推荐用法**
> 写进文档，不在校验里拦。

## 5. 数据表变更（迁移 `0009`）

```sql
-- releases：从"一条记录"变成"一次部署"。
ALTER TABLE releases ADD COLUMN status TEXT NOT NULL DEFAULT 'created';
ALTER TABLE releases ADD COLUMN directory TEXT;          -- 磁盘上的 release 目录
ALTER TABLE releases ADD COLUMN activated_at TEXT;       -- 成为 current 的时刻
ALTER TABLE releases ADD COLUMN finished_at TEXT;
ALTER TABLE releases ADD COLUMN error_code TEXT;
ALTER TABLE releases ADD COLUMN error_message TEXT;

-- application_specs：按 release 版本化（1c 决定 3）。
-- SQLite 改不了主键，因此重建：
CREATE TABLE application_specs_new (
    application_id TEXT NOT NULL REFERENCES applications (id),
    release_id     TEXT,                                  -- NULL = 应用级当前规格（迁移前的老行）
    spec_json      TEXT NOT NULL,
    updated_at     TEXT NOT NULL,
    updated_by     TEXT,
    PRIMARY KEY (application_id, release_id)
);
INSERT INTO application_specs_new (application_id, release_id, spec_json, updated_at, updated_by)
    SELECT application_id, NULL, spec_json, updated_at, updated_by FROM application_specs;
DROP TABLE application_specs;
ALTER TABLE application_specs_new RENAME TO application_specs;
```

`status` 的取值与状态机（**只有这些转移**）：

```
created → deploying → active → superseded
                   ↘ failed
active  → superseded   （被下一次成功部署取代）
active  → removed      （被保留策略清理；只有它不再是 current 时才可能）
```

**兼容性**：`ALTER TABLE … ADD COLUMN` 带默认值，既有行不受影响；`application_specs` 的重建
保留全部既有行（`release_id` 为 NULL）。回滚本迁移会丢掉 `release_id`（可接受：它是本迭代
新增的语义）。

## 8. 验收标准

1. 制品被解包到 `<releases 根>/<release-id>/`，模式 `0750`、属主 `runUser`（1c 决定 4）。
2. `exec.argv[0]` 解析到的**就是** release 里那个文件（不是运维手工放的路径）——
   把 release 目录删掉，应用就起不来。
3. 解包拒绝一切路径穿越（绝对路径条目、`..`、经符号链接逃逸、指向外部的硬链接）。
4. `app.deploy` 走 Operation；健康通过才 `active`。
5. 部署失败时：`current` 回到原版本、原版本仍在跑、新 release 目录被删除、
   Operation 报 `DEPLOY_ROLLED_BACK`。
6. **回滚连配置一起回滚**（`application_specs` 按 release 版本化）。
7. 同一 version 同制品幂等、不同制品 `RELEASE_CONFLICT`。
8. 保留策略只删非 current 的、最老的；`keepLast` 生效。
9. `runtime: java` 的部署能在真机上跑起来（真 JAR + 真 JVM）。
10. `make ci` / `make verify-linux` / `make verify-db` 全绿，迭代 0–2 的回归全部继续通过。

## 11. 已冻结的决定（原「待确认事项」，2026-09-24 拍板）

> 三条**全部按推荐值**冻结。冻结的是取值，不是实现细节——实现时若发现某条不可行，
> 必须先改本节并记录原因，不得默默偏离（沿用 1c/2 的做法）。

### 决定 1：切换机制 = **A**（`current` 符号链接）

| 选项 | 说明 |
| --- | --- |
**采纳 A**：`current` 符号链接 + unit 只写一次；切换 = 原子 rename + restart。
（备选 B：每个 release 一个 unit 文件，写明具体目录。）

A 的理由：与 1c 留在 `unitfile` 里的注释和 proc 适配器的既有引用一致；切换原子且不需要
daemon-reload；「跑的是哪个版本」只有一处真相。B 的好处是 `systemctl cat` 直接可读。

### 决定 2：Java 的表达方式 = **A**（全写进 argv）

**采纳 A**：Java 路径与 JVM 参数**都写进 `exec.argv`**，不新增 `java.*` 字段；
`runtime: java` 只决定校验（argv[0] 必须是绝对解释器路径）。
（备选 B：新增 `java.path` + `java.args`，部署时拼出最终 argv。）

A 的理由：**只有一处 argv 拼装**，不引入第二种语义；「显式配置 Java 路径与 JVM 参数」这条
路线图要求由 argv 满足。B 的好处是 JVM 参数与业务参数在模型上分开，将来可以做「按
`resources.memoryMaxBytes` 推导 `-Xmx`」这类联动——但那是猜测，现在不做。

### 决定 3：**新增** `DEPLOY_ROLLED_BACK`（D10）

采纳：它回答了部署失败后运维的第一个问题——「现在线上跑的是哪个版本」。

## 12. 3a 实现记录（2026-09-24）

范围见第 2 节：`ReleaseAdapter` 端口与解包实现、manifest 增量字段与严格校验、argv 的解析规则。

### 逐文件要点

**领域（`internal/domain/appspec.go`）**
- `SpecArtifact` 新增 `Version` 与 `FileName`；`SpecResources`（`CPUQuotaPercent` / `MemoryMaxBytes`）、
  `SpecRelease`（`KeepLast`）与 `ApplicationSpec.Resources/Release`。
- `ReleaseRootDir` 从 `runtime/unitfile` **归位到 domain**：1c 时它临时住在渲染包里，而迭代 3
  有四个地方要用它（unit 渲染、runtime 建目录、release 解包、argv 解析）——四处各拼一次就是
  把「约定」变成四个可能漂移的实现。同时新增 `CurrentReleaseDir`。
- `ResolveArgv`（D4）与 `MaterializedFileName` / `Materializes`。

**共享包（`internal/sysuser`）**
- `Resolver` + `OSLookup` 从 `runtime/systemd` 抽出来：现在 runtime/systemd 与 release/local
  都要把文件 chown 给运行用户，而「这个文件到底属于谁」在两处各算一遍迟早会有先漂移的那个。

**端口（`internal/application/ports.go`）**

`ReleaseAdapter`：`Materialize` / `Activate` / `Remove` / `List`（见 D1 的形状）。

**适配器（`internal/adapters/release/local`）**
- `local.go`：路径前缀重定向（与 systemd/files 同源，测试里就能断言真实产物）、
  **解到 `.staging` 再改名**、`current` 用**相对名字**做符号链接目标（整个 releases 根可以被
  整体搬走或换前缀）、`Remove` 拒绝删 current、`List` 跳过 current 与暂存目录。
- `unpack.go`：四条策略 + `stripComponents`；路径穿越的三道防线写在文件头的注释里
  （条目名逐条校验、**逐级检查父目录链且拒绝穿过符号链接**、目标同名是链接时拒绝写入），
  硬链接额外要求目标在 release 之内。链接条目**延迟到最后统一建**，顺序问题因此消失。

**manifest（`internal/adapters/manifest/manifest.go`）**
- wire 层新增 `artifact.version` / `artifact.fileName`、`resources`、`release`。
  `release.keepLast` 用**指针**：没写要走默认值，而显式写 0 是非法值——指针才能把两者分开。

**unit 渲染（`internal/adapters/runtime/unitfile/unit.go`）**
- 在渲染时解析 argv（D4），并把解析结果放进 `Rendered.Argv`：**这是 argv 最后一次被使用的地方**，
  把解析放这里而不是散在调用点，「怎么解析」与「谁来执行」就只有一个来源。

### 对规格的补充与偏离

1. **D4 修正：只解析 `argv[0]`**（已就地改第 3 节与第 11 节的措辞）。原写法是「每个元素按同一
   条规则解析」，写测试时发现它会把 `-Xmx512m`、`-Dlogging.file=/var/log/app.log` 这样的参数
   **静默改写成路径**——不是报错，是行为变了。
2. **删掉「`runtime` 与 `argv[0]` 形态配对」的校验**（原 §4 的校验清单里有一条）。1c 起就允许
   绝对 `argv[0]`，把它收紧成非法属于改变必填性/形态的破坏性变更。「编译产物住在 release 里」
   改为**推荐用法**写在文档里。
3. **新增 `ARTIFACT_UNPACK_FAILED`**（409 / 退出码 30）：制品解不开与 manifest 非法是两件事，
   运维要做的事也不同。已补进 D10 的表。
4. **新增 `artifact.fileName`**（规格 §4 里没有）：单文件制品（Go 二进制、单个 JAR）没有归档
   自带的名字，而「叫什么」决定了 argv 里怎么写它。**可选**，缺省取**相对的** `argv[0]`。
5. **`artifact.version` 从「必填」改成「可选 + 缺省按 digest 派生」**：必填是改变必填性的
   破坏性变更，而派生值同样唯一（`sha256-` + digest 前 12 位）。
6. **`artifact.digest` 现在是严格校验的**：原先只查 `sha256:` 前缀，于是长度不对的写法能过校验、
   到部署时才以「找不到制品」失败——那是个把人带偏的报错。
7. **`release.keepLast` 不接受 0**（规格写的是「0 = 不自动清理」）：制品永远在制品库里、
   重新解包即可，因此「永不清理 release 目录」没有真实价值，只会把盘慢慢占满。少一个取值，
   也少一处「没写 vs 显式 0」的歧义。

### 发现

1. **`-Xmx512m` 被当成相对路径**（写测试时撞出来）：见偏离 1。它是本里程碑最有价值的一条——
   这类错误不会报错，只会让进程收到被改写的参数。
2. **符号链接的目标与硬链接的目标是两条不同的规则**：符号链接可以指向 release 之外（共享库、
   `/etc` 下的配置是正常用法），硬链接必须在 release 之内（它是同一个 inode 的第二个名字）。
   第一版对两者用了同一条校验，测试里的「指向外部的符号链接」用例把它顶了出来。
3. **`fileName` 必填会破坏所有 1c manifest**：`unpack` 省略时策略默认就是 `none`，于是每一个
   既有 manifest 都会提交不了。改成可选 + 缺省取相对 `argv[0]`，并保留「argv[0] 指向发布目录
   之外的既有程序」这种 1c 形态（`Materializes()` 返回 false，部署时跳过物化与切换）。

## 14. 3b 实现记录（2026-09-24）

范围见第 2 节：部署与回滚走 Operation、release 状态与目录的持久化、`current` 切换、
保留最近 N 个、失败自动回到上一稳定版，以及 `application_specs` 按 release 版本化。

### 逐文件要点

**持久化（`migrations/0009_release_deploy.sql`、`internal/adapters/sqlite`）**
- `releases` 加 `status` / `directory` / `activated_at` / `finished_at` / `error_code` /
  `error_message`；`application_specs` 改成「应用 + release 一行」（1c 决定 3）。
- **两处 SQLite 陷阱**，都写进了迁移的注释与用例：
  1. `PRIMARY KEY (application_id, release_id)` 里 `release_id` 为 NULL 时**不受约束**
     （SQLite 认为 NULL 互不相等），`ON CONFLICT (application_id, release_id)` 对它永远不触发
     ——每写一次多一行，而读的时候只取第一行，看起来一切正常。用偏索引 + 带 `WHERE` 的冲突
     目标钉死。
  2. `GetApplicationSpec` 必须带 `release_id IS NULL`：迁移之后同一个应用有多行，只按
     `application_id` 查会取到**任意一行**，而「任意一行」在测试里往往恰好是对的。
- `MarkReleaseDeploying` / `ActivateRelease`（**一个事务**里 supersede 旧的 active、activate
  新的）/ `FailRelease`（清空 `directory`，因为失败的目录会被删掉）/ `MarkReleaseRemoved`
  （只在非 active 上生效）/ `ActiveRelease` / `GetReleaseByVersion` / `PreviousRelease`。

**领域（`internal/domain/release.go`）**
- `ReleaseStatus` 六态与合法转移；`Rollbackable()` 只认 `active` 与 `superseded`——
  `failed` 从没跑成功、`removed` 的目录已经没了。
- `PlanReleaseRemoval(releases, keepLast)`：**纯函数**，保留 = {current} ∪ {最年轻的
  keepLast-1 个仍带目录的版本}，删除从老到新。current **不占名额**（回滚到旧版本之后，激活的
  那个可能比某些 superseded 的更老，把它当"最新的一份"去数会让保留集合算错）。

**编排（`internal/application/deploy.go`）**
- `PrepareDeploy`（创建期：解析制品、按 D2 的规则找到或新建 release 行、把这一版的规格写下来）、
  `PrepareRollback`（创建期选定回滚目标）、`ResolveDeployOperation`（接缝）、
  `ExecuteDeploy` / `ExecuteRollback` 共用一个 `apply`。
- 失败收尾统一在一处：能切回原处就切回（**连配置一起**）、删掉本次新建的目录、把 release 记成
  `failed`；**回滚也失败时刻意不报 `DEPLOY_ROLLED_BACK`**——那个码说的是「已经回到上一个稳定
  版本」，而这里没有，所以返回原始错误码并在消息里写明「当前没有正在运行的版本，需要人工介入」。
  把这两种情况混成一个码，会让运维在最需要立刻动手的时候以为没事。
- 第一次部署失败：没有可回退的版本 → 停掉 unit + **撤掉 current 指针**（留着它去指一个马上要
  删掉的目录，会让「现在跑的是哪个版本」这句话指向不存在的东西）。

### 对规格的补充与偏离

1. **D6 第 5 步修正：就绪由部署流程轮询**（已就地改第 3 节）。1c 的 `runtime.start` **不等待
   就绪**——「启动 ≠ 就绪」是它刻意保留的区分。因此 `Start` 之后由部署流程轮询 `Health`
   （200ms 间隔），直到 `Ready` 或超过 `spec.Health.StartTimeout`。
2. **换版本必须先停掉上一个版本**（实现时被容器验证抓出来，见「发现 1」）：`Start` 对已经
   active 的 unit 是**幂等的 no-op**，那是 `runtime.start` 要的性质，但对部署不适用。
3. **`ReleaseAdapter` 增加 `Deactivate`**：第一次部署失败时要撤掉 current 指针，而
   `Remove` 刻意拒绝删 current。与其让编排层去动符号链接（那是适配器的文件系统职责），
   不如把这个动作显式加进端口。
4. **部署类操作拒绝 `dryRun`**（与 runtime.* / backup.* 同源的理由）：适配器端口没有
   dry-run 语义，接受它就会变成「以为只是预演、其实真的换了版本」。
5. **同一版本重复部署是幂等的**：要上的版本已经是当前版本时，`PrepareDeploy` 返回
   `AlreadyActive`，**不产生 Operation**（HTTP 200 而不是 202）。而 `created`/`failed`/
   `removed` 状态的行会被**复用**（同一次部署的重试、或者重新部署一个被清理过的版本）；
   `superseded` 的行则走「把既有版本再应用一次」——也就是回滚。
   目录已存在时**跳过物化**，正是为了这条路能走通（制品不可变，重新解一遍只会撞上
   「目录已存在」）。
6. **回滚默认目标是「最近一个曾经激活、且状态仍可回滚的版本」**（`PreviousRelease`），
   而不是「第二新的记录」：从没部署成功的版本不能当回滚目标。

### 发现

1. **换版本不重启就不会生效——这是容器验证抓出来的真实缺陷。** 第一次跑容器断言时，
   第二版部署一直以「15 秒内未就绪」失败，而原因是 `systemctl start` 对**已经 active 的
   unit 是 no-op**，旧进程继续占着它自己的端口。修法是部署流程在 `Start` 新版本之前先
   `Stop` 上一个版本（回滚路径同理，方向相反）。**这条只有真实容器能发现**：假适配器不区分
   「start 一个没运行的」与「start 一个已经在跑的」。
2. **`stat -c %a` 不跟随符号链接**：它报的是链接自己的模式（永远是 777），要 `stat -L`。
   容器断言第一版因此断言了错误的数字。
3. **`ls -d */` 会把 `current` 数进去**（指向目录的符号链接匹配 `*/`），于是「目录数不超过
   keepLast」的断言永远差一。改用 `find -type d`（不跟随符号链接）。
